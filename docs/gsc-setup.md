# GSC検索パフォーマンスの自動取得（セットアップ手順）

2026-08-10導入。**ユーザー作業は3ステップ・15分程度**。一度やれば以後は自動です。

## なぜこれを作ったか

Search Console は画面もAPIもログインが要るため、セッション（Claude）からは実測値を読めません。
代わりに **GSCの通知メールを読む** 方法を試しましたが、精度が足りませんでした。
2026-08-10時点で届いていたメールは全期間で5通だけ：

| 種類 | 通数 | そこから取れる数値 |
|---|---|---|
| セットアップ案内 | 2 | なし |
| インデックス未登録の新要因 | 2 | **要因の種類のみ。対象URLも件数も無い** |
| 「クリック数が10に到達」 | 1 | **「10以上」という下限値のみ** |

表示回数・CTR・平均掲載順位・クエリ別・ページ別は**一切届きません**。月次パフォーマンス
レポートも来ていません。つまりメール経路では `docs/operations.md` の「実測サマリ」を
埋められません。

そこで、外向き通信ができる GitHub Actions から Search Console API を日次で叩き、
結果をリポジトリに保存する形にしました。以後セッションは**コミット済みのJSONを読むだけ**で
よくなり、ログインも外向き通信も要りません。

## セットアップ（3ステップ）

### 1. Google Cloud でサービスアカウントを作る

1. https://console.cloud.google.com/ でプロジェクトを作る（既存のものでも可）
2. 「APIとサービス」→「ライブラリ」→ **Google Search Console API** を有効にする
3. 「APIとサービス」→「認証情報」→「認証情報を作成」→ **サービスアカウント**
   - 名前は任意（例: `gsc-reader`）。ロールの付与は**不要**（GSC側で権限を渡すため）
4. 作ったサービスアカウント →「キー」→「鍵を追加」→「新しい鍵を作成」→ **JSON**
   → JSONファイルがダウンロードされる
5. そのサービスアカウントの**メールアドレス**（`...@....iam.gserviceaccount.com`）を控える

### 2. GSCのプロパティに、そのサービスアカウントを追加する

1. https://search.google.com/search-console でプロパティ
   `https://animedia-khaki.vercel.app/` を開く
2. 左下の「設定」→「ユーザーと権限」→「ユーザーを追加」
3. 上で控えた**サービスアカウントのメールアドレス**を入れ、権限は **「制限付き」** でよい
   （読み取りだけしかしないため。「フル」にする必要はありません）

### 3. 鍵を GitHub Secrets に登録する

1. リポジトリ →「Settings」→「Secrets and variables」→「Actions」→「New repository secret」
2. 名前: `GSC_SERVICE_ACCOUNT_JSON`
3. 値: ダウンロードしたJSONファイルの**中身を丸ごと**貼り付ける（改行込みでそのまま）

**鍵はリポジトリにコミットしないでください。** `scripts/check-gsc.js` が
「書き出すJSONに秘密鍵・アクセストークン・サービスアカウントのアドレスが混入しないこと」を
機械的に検査していますが、鍵そのものの取り扱いは人の責任です。

## 動作確認

- リポジトリの「Actions」→「GSC検索パフォーマンスの日次取得」→「Run workflow」で手動実行
- 成功すると `content/analytics/gsc/<期間終端日>.json` がコミットされる
- **鍵が未登録の間、このワークフローは何もせず終了します**（静かにスキップ）。
  失敗のIssueが毎日積み上がることはありません

## 取得しているもの

`scripts/fetch-gsc.js` が、直近28日ぶん（GSCの確定待ちを考慮して終端は3日前）を取ります。

| キー | 内容 |
|---|---|
| `totals` | 期間合計のクリック・表示回数・CTR・平均掲載順位 |
| `daily` | 日別の推移 |
| `queries` | 検索クエリ別の上位100件 |
| `pages` | ページ別の上位100件 |

`totals.position`（平均掲載順位）は**表示回数で重み付け**して計算しています
（日別の単純平均だと、表示の少ない日が同じ重みで効いて歪むため）。

## 運用

- 実行は毎日1回（06:40 JST 前後）。GSCのデータは数日遅れて確定するので時刻の精度は不要
- 一時的なエラー（429・5xx）は指数バックオフで再試行する
- 恒久的なエラー（401・403など）は即座に失敗し、**GitHub Issue**（ラベル `gsc-snapshot`）に出る
- 3種類のクエリは独立していて、1つ失敗しても残りは取得してファイルに書く
  （そのうえで終了コードは1にして、取りこぼしをIssueで知らせる）

## この仕組みで取れないもの

- **インデックス登録の状況**（「重複しています」「ページにリダイレクトがあります」などの
  対象URL）は Search Analytics API では取れません。URL Inspection API は1URLずつの
  呼び出しで日次クォータもあるため、今回は入れていません。
  GSCの「ページのインデックス登録」レポートは引き続き画面で見てください。
- **Vercel Analytics**。Hobbyプランはカスタムイベントを記録せず、公開APIもありません。
  自前の `/admin/analytics`（Supabase）は別系統で、必要になったら同じ形で自動化できます。
