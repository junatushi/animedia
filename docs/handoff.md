### #41 のVercelビルド失敗を直した（原因特定の記録・再発しやすい罠）

`claude/mastodon-delivery-traffic-1ggim6`（8/6の日次巡回の成果・1,359行）が
**PR未作成のまま放置されていた**ので起票したところ、**VercelのデプロイだけがCI緑のまま失敗**した。

**真因**: `app/anime/[id]/opengraph-image.tsx` は `runtime = "edge"` なのに `getWorkData` を
importしている。#41が`getWorkData`に足した過去クールのフォールバックは
`content/snapshots/*.json`（64ファイル・5.1MB）を動的importで読むが、**Edge runtimeの
バンドルは自己完結が必要（fsが無い）なため、動的importが遅延ロードにならず丸ごと
インライン化される**。

実測: `.next/server/app/anime/[id]/opengraph-image/route.js` が **16KB → 5,040KB**、
`.next/server` 合計が **21MB → 26MB**。VercelのEdge Functionのサイズ上限（プランにより1〜4MB）を超える。

**なぜ気づきにくいか**: ローカルビルドにもGitHub ActionsのCIにも**サイズ上限が無い**ので
両方緑のまま通り、Vercelだけがデプロイ段階で短時間に落ちる。
→ 対処: ライブ取得だけの`lib/getWorkDataLive.ts`を切り出し、edgeのOG画像はそちらを使う。
**edge runtimeのルートを足すときは、重い静的データを引き込んでいないかビルド出力の
サイズで確認すること**（CIでは検出できない）。

**切り分けの方法（PCが無くても効く）**: Vercelのログが見られなくても、
**mainブランチをローカルでビルドして`.next/server`のサイズを比較**すれば原因箇所は特定できる。
今回はこれで`app/anime/[id]`だけが5MB膨らんでいることを突き止めた。

## 踏んだ落とし穴（再発防止）

- **SSRページはHTMLを取って中身を数える**（⑦-10）。ブラウザの表示は当てにならない。
- **dev server起動中に`rm -rf .next && npm run build`すると`.next`キャッシュが破損する**。
  ビルド前に必ずサーバーを止める。
- **`gh` CLIはこの環境に入っていない**。GitHubのIssue・Actions実行履歴を見たいときは
  GitHub MCPツール、またはリポジトリが公開なので`https://api.github.com/repos/junatushi/animedia/...`
  をWebFetchで直接叩く。
- **サンドボックスによっては外向き通信が全面的に遮断される**（2026-08-05のセッションでは
  `animedia-khaki.vercel.app`・`public.api.bsky.app`・`mastodon.social`のすべてが
  プロキシで403。SNSの実投稿・フォロワー数は取得できなかった）。
  その場合でも**ローカルで本番ビルドを起動すればHTMLの検証はできる**（今回の発見はこれで得た）。
- **`node scripts/check.ts`から`.tsx`はimportできない**（NodeはJSXを解釈しない）。
  検査したいロジックは素の`.ts`に置く（`lib/workTitle.ts`がその例）。
- Annict GraphQLスキーマにレンタル/サブスク区別フィールドは無い（introspection確認済み）。
- サーバー/クライアントで年・シーズン解決ロジックがズレるとSSRの`initialData`と表示が
  食い違う。`lib/resolveSeasonParams.ts`に共通化済み、変更時は両方への影響に注意。
- `ServiceTag.key`は`string`型（`lib/types.ts`）。
