# 引き継ぎメモ（2026-08-25 その2・ISRの作り直し方を根本から変えた）

## 最重要: 前のメモの「削減の見込み」は**間違っている**

同じ日の前半（下の1本目のメモ／PR #97）で「再検証を900→3600秒に延ばしたのでISR Writesは
6万〜11万件に減る見込み」と書いたが、**この変更では1件も減らない**。救済措置をもらった直後に
検算して判明したので訂正した。訂正の内容は`docs/operations.md`の㉝「追記（同日・重要な訂正）」。

理由は算数。超過時の30日実測を1日あたりに直すと Edge Requests 10,300件・ISR Writes 9,882件・
ISR Reads 6,533件で、**書き込みが読み出しを上回っている**（リクエストの96%が再生成）。
sitemapの約7,051ページへ1日10,300リクエストが分散すると**1ページあたりの再訪間隔は平均16.4時間**
になる。revalidateがこれより短ければ訪問のたびに必ず期限切れ＝毎回書き込みになる。
900秒も3600秒も16.4時間より遥かに短いので結果は同じだった。

**この規模では時間ベースのISRという仕組み自体が長い裾に対して機能していない。**
「アクセスが薄いページほど、来訪のたびに作り直す」装置になっており、ページを増やすほど悪化する。

# 引き継ぎメモ（2026-08-25・Vercel利用上限超過への対応）

## 結論: 原因は「アクセス過多」ではなく「同じページを何度も作り直していた」こと

前日（08-24）の402停止は、Vercel Hobbyの30日利用上限の超過による**プロジェクトのPause**だった。
ユーザーがダッシュボードで確認した実測値は Fluid Active CPU 12h46s/4h・ISR Writes 296,449/200,000・
Fluid Provisioned Memory 489.1/360 GB-Hrs の3指標が超過。一方で Function Invocations 389K/1M・
Edge Requests 309K/1M・ISR Reads 196K/1M は**すべて上限内**だった。
訪問者の数は問題なく、**再生成の回数が問題**だったということ。

**ユーザーはアップグレードしない方針を決めた**（費用が発生するため）。よって利用量を上限内に
収める方向で対処した。詳細な原因分析と学びは`docs/operations.md`の㉝に書いた。

## やったこと（コード変更あり・全検査538件OK・ビルドOK）

1. **`vercel.json`を新規作成**（このリポジトリには存在しなかった）。`ignoreCommand`で
   `content/analytics/`・`content/coverage/`・`content/demand/`・`docs/`しか変更していない
   コミットは本番デプロイを起こさないようにした。**Vercelはデプロイごとに独立したISRキャッシュを
   持つ**ため、デプロイ＝キャッシュ実質全消去＝全ページ作り直しになる。mainへ自動コミットする
   cronは1日5本あり、うち3本はサイトの表示に一切使わないデータを書いていた。
   実際のコミット履歴12件で検証し、9件がスキップ・表示データを運ぶ`fetch-upcoming`だけが
   デプロイされることを確認済み。
2. **ISRの再検証を1時間（3600秒）に統一**。トップ900・シーズン600・作品900・声優900・
   ランキング600・独占配信600・サービス別600・`/api/work`900・埋め込み900・ICS900 → すべて3600。
   **これは表示を速くする変更**（キャッシュが効く時間が4〜6倍になる。ISRは期限切れ後も
   stale-while-revalidateで古いHTMLを即返して裏で作り直すので、待たされる場面は増えない）。
3. **データ層のTTLも3600へ**（`lib/annict.ts`の`next.revalidate` 600→3600、
   `lib/getSeasonData.ts`の`CURRENT_YEAR_REVALIDATE` 900→3600）。**ここが最大の落とし穴だった**:
   App Routerの実効revalidateは「ページの指定」と「描画中のfetch/unstable_cacheのTTL」の
   **低いほう**になるため、2だけでは実効900のままで無意味だった。
   `.next/prerender-manifest.json`を実測して発覚し、修正後は13ページすべてが3600になったことを
   同じ方法で確認した。**revalidateを変えたら必ずビルドして実効値を見ること**（CLAUDE.mdに追記済み）。
4. **`middleware.ts`が匿名リクエストでSupabaseへ往復しないようにした**
   （`lib/supabase/middleware.ts`に`hasAuthCookie`を追加）。Provisioned Memory 489.1 GB-Hrs ÷ 2GB
   （Hobbyの既定割当・変更不可）＝約245インスタンス時間に対し実CPUは12時間しかなく、
   **稼働時間の約95%がI/O待ち**だった。Vercelの課金はActive CPUがI/O待ちで止まる一方
   **Provisioned Memoryは止まらない**。middlewareは画像以外の全リクエストで`auth.getUser()`＝
   Supabaseへの往復を1回していた。ログイン中の利用者の挙動は一切変えていない。
5. **`warm-cache.yml`を毎時→6時間おき、`WORK_LIMIT`を60→30**。この巡回はページのrevalidate
   （900秒）より実行間隔（60分）が長かったため、**毎回必ずキャッシュ期限切れに当たり67ページを
   書き直していた**（30日で約46,000件＝ISR Writes全体の約16%）。「温め」ではなく
   「強制的な書き直し」になっていた。

## 削減の見込み（推定。Vercel側の内訳は見られないので実測で答え合わせが要る）
