# 引き継ぎメモ（2026-09-03・表示速度。トップ/シーズン一覧の重さを削った）

## 依頼

利用者から「アニメ視聴ガイドの表示が2秒以上。**Vercelの無料枠内のまま**速くしてほしい」。
確認したところ対象は**トップ／シーズン一覧**で、他のページ種別は未検証とのこと。

## やったこと（PR: `claude/anime-guide-performance-n0vvh2`）

詳細と数字は`docs/operations.md`の㊴。要点だけ:

1. **リンクの先読みを「画面内」から「素振り（hover/touchstart）」に変えた**。
   App Routerの`<Link>`は既定で画面に近づいたリンクのRSCペイロードを先読みする。
   実測でシーズン一覧を下まで見ると**120リクエスト・528KB**が押されてもいないページの
   ために飛んでいた（フッターの他クールリンクは**1本181KB**、ヘッダーの`"/"`は全ページで
   初期表示と同時）。`components/IntentLink.tsx`に一本化。
2. **supabase-jsを初期JSから外した**（動的import＋認証Cookieの門番）。
   トップのFirst Load JS **181KB→117KB**。
3. **カードのアイコンをスプライト化**、**カードを12枚ずつ`<Suspense>`で包んだ**。
   後者は同じビルド同士の比較で**TBT 1,404ms→1,135ms（−19%）**。
4. 速さを測る道具を足した（`node scripts/measure-pages.js`）。手元のPC専用。
5. 逆戻り防止の検査を2節追加（4通りの壊し方で落ちることを確認済み）。

## 効果（5回の中央値・CPU4倍/1.6Mbpsのスマホ相当条件・`/season/2025/summer`）

| 指標 | 変更前 | 変更後 |
|---|---|---|
| 初期表示のバイト | 268KB | 198KB |
| スクロール中の通信 | 120リクエスト・528KB | 0件・0KB |
| 初期JS | 181KB | 117KB |
| TBT | 1,290ms | 1,181ms |
| FCP / LCP | 872ms | **872ms（変わらず）** |

## 正直に書いておくこと

- **FCP/LCPは1msも動いていない。** ローカルはサーバーが即答するため、削ったバイトが
  効くのは実回線のときだけ。「出るまで」ではなく「通信量」と「触れるまで」が改善した。
- **本番の実地測定はできていない**（この環境から本番URLへ出られない／PSI APIは共有枠が上限）。
  利用者が**PSIのAPIキーを渡す**と回答済みなので、受け取り次第 本番のLCP/TBTと
  CrUXの実ユーザー値で答え合わせをすること。
- 先読みを止めたぶんVercelの Function Invocations・ISR・転送量が減るはずだが、**削減量の
  実測はまだ無い**。㉝のチェックポイント（2026-09-18）で確認する。

## 次にやるなら（どれも見た目か構造を変えるので、独断で入れない）

残るTBT約1,100msの主因は「172枚のカードを1つのクライアントコンポーネントで水和すること」
そのもの（`/anime`61ノード=122ms → `/season`8,360ノード=1,382msという実測がある）。

- A. カード一覧をReactの水和から外す（イベント委譲）…効果最大・変更最大
- B. カードの`backdrop-filter: blur(10px)`をやめる…見た目が変わる
- C. サムネイル（640×360・平均40KB・計4.4MB）を表示サイズに合わせて作り直す
- D. middlewareの対象URLを絞る

## ユーザーにやってほしいこと

- **PageSpeed InsightsのAPIキー**（本番の実測用）。もしくは pagespeed.web.dev で
  トップ・シーズン一覧を測って、スコアとLCP/TBT/CLSの数字を貼ること。
- 上のA〜Dのうち、どこまで踏み込んでよいかの判断（Bは見た目が変わる）。

# 引き継ぎメモ（2026-08-25 その2・ISRの作り直し方を根本から変えた）

## 最重要: 前のメモの「削減の見込み」は**間違っている**

同じ日の前半（下の1本目のメモ／PR #97）で「再検証を900→3600秒に延ばしたのでISR Writesは
6万〜11万件に減る見込み」と書いたが、**この変更では1件も減らない**。救済措置をもらった直後に
検算して判明したので訂正した。訂正の内容は`docs/operations.md`の㉝「追記（同日・重要な訂正）」。

理由は算数。超過時の30日実測を1日あたりに直すと Edge Requests 10,300件・ISR Writes 9,882件・
ISR Reads 6,533件で、**書き込みが読み出しを上回っている**（リクエストの96%が再生成）。
sitemapの約7,051ページへ1日10,300リクエストが分散すると**1ページあたりの再訪間隔は平均16.4時間**
になる。revalidateがこれより短ければ訪問のたびに必ず期限切れ＝毎回書き込みになる。
900秒も3600秒も16.4時間より遥かに短いので結果は同じだった。

**この規模では時間ベースのISRという仕組み自体が長い裾に対して機能していない。**
「アクセスが薄いページほど、来訪のたびに作り直す」装置になっており、ページを増やすほど悪化する。

## 状況

- **本番サイトは復旧している**（08-25 14:11 UTCに`verify-production.yml`を手動実行してsuccess。
  SSRのHTMLも正常）
- ユーザーが救済措置を取得。**30日だけ通常の3倍枠**（ISR Writes 600,000 / Active CPU 12h /
  Provisioned Memory 1,080 GB-Hrs）。**30日後に通常枠へ戻り、超えていればまた停止する**
- PR #97 はマージ済み（08-25）。PR #104 が今回の訂正と本命の対策

## やったこと（PR #104）

1. **長い裾の`revalidate`を604800秒（1週間）に**（作品・声優・サービス別・シーズン・ランキング・
   独占配信）。`lib/annict.ts`のfetchも1週間＋タグ`"annict"`（ここが短いと実効値が引きずられる）
2. **鮮度は時間ではなく「指名」で取りに行く**。`app/api/revalidate/route.ts`が
   `revalidateTag("annict")`と現在クールへの`revalidatePath`を実行し、
   `.github/workflows/revalidate.yml`が1日2回叩く。認証は既存の`NOTIFY_CRON_SECRET`を
   使い回すので**新しいシークレットの設定は不要**
3. **長い裾の64%を事前生成に移した（最大の効果）**。事前生成したページはISR Writesを
   1件も消費しない（デプロイ成果物に含まれる）。事前生成していないページはデプロイのたびに
   キャッシュが消え、最初に見に来た人の分だけ必ず書き込みが起きる。**この床はrevalidateを
   いくら延ばしても消せない**。声優ページ4,483件＋過去シーズン64件を`generateStaticParams`で
   全件焼くようにした。事前生成は566→5,113ページ、**ビルドは54秒**（増分約20秒）
4. **OGP画像が完全に無キャッシュだった**。`app/anime/[id]/opengraph-image.tsx`は
   `force-dynamic`で毎リクエスト関数が起動し、中でAnnictとGoogle Fontsへ**計3往復**していた。
   I/O待ちはActive CPUには出ないがProvisioned Memoryには出るので、メモリ課金の主要な発生源の
   ひとつだったとみられる。明示の`Cache-Control`を入れた
5. **Route Handlerは`export const revalidate`ではなくCache-Controlヘッダが実効値**。
   埋め込みと`/api/work/[id]`が`s-maxage=900`のままで、1の変更が効いていなかった→86400
6. `scripts/check.ts`に「ISRの再生成頻度」節（12項目）。数字を戻す変更は画面を見ても
   気づけないので機械で見張る
