# 運用手順書（runbook）

「アニメ視聴ガイド」を継続運用するための定期作業まとめ。
何を・いつ・どうやるかを固定し、担当が変わっても回るようにする。

シーズンの区切り（目安）:
- 冬 1月 / 春 4月 / 夏 7月 / 秋 10月 開始。各クールとも開始月の頭に切り替わる。

## ⑨ AI引用モニタリング（週1回・2026-07-08開始）

ChatGPT・Perplexity等の生成AI検索に、このサイトが情報源として挙がるかを定点観測する。
やることは「想定質問を投げて、回答にサイト名/URLが出るか記録する」だけ。

**チェック用の質問例（毎回同じ文言で聞くと変化が比較しやすい）**:
- 「今期（{年} {季節}クール）のアニメを配信サービス別に一覧で教えて」
- 「{今期の注目作タイトル} はどこで配信されている？」（TOP5の中から1〜2本を機械的に選ぶ）
- 「今期アニメの配信状況が一覧でわかるサイトはある？」
- 「アニメ視聴ガイド というサイトを知っている？」（エンティティ認識の確認）

**記録すること**（表・メモ形式は自由）:
- 日付
- 使ったAIサービス（ChatGPT / Perplexity / Google AI Overviews等）
- 聞いた質問
- サイト名・URLが回答に出たか（出た場合は文脈も一言メモ）

**運用方針**: 週1回、無理のない範囲で。すぐに結果が出るものではないため、
数ヶ月単位で「引用され始めた/頻度が増えた」等の変化を追う想定。
記録先は特に指定しない（ユーザーが使いやすい場所でよい。将来的にこの
`docs/operations.md`に「これまでの結果サマリ」を追記していく形でもよい）。

**位置づけ（2026-08-17）**: ⑬（流入リード発掘）を凍結したため、集客施策の効果測定は当面この⑨に一本化する。現戦略（データ供給元／AI検索時代への布石。`docs/growth-strategy-2026-08.md`・`docs/ai-era-strategy-2026-08-13.md`）が効いているかを「AI検索で被引用されるか」で測る面なので、方向性が合っている。

## ⑩ 見込みユーザー/コミュニティ候補の発掘（outreach-scout・2026-07-13導入）

`docs/sns-growth-research.md`（2026-07-08）の結論どおり、「見込み客を自動で見つけて接触する」は
X APIの従量課金化・Bluesky/Mastodonの日本語アニメ層の薄さから費用対効果が合わない。そのため
**自動化するのは候補の洗い出しまで**とし、実際の参加・掲載依頼・リプライは常に人力で行う。

**やること**: `outreach-scout` サブエージェントを起動する（「見込みユーザーを探したい」「アウトリーチ候補が
欲しい」等）。Discordサーバー・まとめ/感想サイト・「配信どこ」系の困りごと・Xの公開言及（検索エンジン
経由のみ）の4カテゴリを軽くWeb検索し、出典URLつきの候補を `docs/outreach-candidates.md` に追記する。

**その後の人力アクション**（コードでは自動化しない）:
1. 気になるDiscordサーバーに実際に参加し、自己宣伝ルールを確認した上で自然に交流する。
2. まとめ/感想サイトへの掲載依頼・言及依頼は、サイトごとの問い合わせ方法に従って手動で送る。
3. 毎回いきなりURLを貼らない（`docs/sns-growth-research.md` にある通り、多くのコミュニティは
   自己宣伝を規制している）。

## ⑪ 声優個人ページの代表作追記（`/person/[name]/...`・2026-07-13導入）

声優個人ページの「代表作（役名付き）」は、AnnictのGraphQL APIには「声優→出演作品」の逆引きクエリが
存在しない（`Person`型に`castsCount`はあるが作品一覧を返すフィールドが無い。2026-07-13に
introspectionで確認済み）ため、全出演作品を機械集計すると全クール分のAnnictデータを舐める必要があり
負荷が大きい。そのため**「今期の出演作品」はこれまでどおりAnnictの実データで自動表示**し、
**「代表作＋役名」だけを人力で追記**する運用にした（`content/works/{id}.json`の人力コンテンツと同じ思想）。

**情報源について（⑧の「Wikipediaは使わない」ルールの例外）**: ⑧の作品あらすじは一次情報のみ
（Wikipedia不可）だが、声優の代表作リストは2026-07-13にユーザーの明示的な許可で**今回に限り
Wikipediaの利用を可**としている。今後追加する場合も、**まずは声優個人の公式サイト・所属事務所の
プロフィールページを優先**し、無ければWikipediaを使う（このページのみの運用。他のコンテンツに
この例外を広げない）。

**追記手順**:
1. `content/people/filmography.ts` の `PERSON_FILMOGRAPHY` に、声優名（Annictの`casts.name`と
   完全一致する文字列）をキーとしてエントリを追加する。
2. `works`（作品名・役名のペア）、`sourceUrl`（出典URL）、`confirmedDate`（確認日）を人力で埋める。
   推測・創作はせず、出典に明記されている範囲のみを書く。
3. 追記後は `npx tsc --noEmit` で型エラーが無いことを確認する。
4. 対象は「今期2作品以上に出演」（`app/person/.../page.tsx`の`MIN_APPEARANCES`）でページ化されている
   声優から、注目度・人気順に都度追加する運用（全声優を一括整備する保守コストは避ける）。

作品個別ページ（`/anime/[id]`）の「あらすじ」「見どころ」「出版社」はAnnictに構造化データが
無いため、公式サイト等の一次情報を人が確認しながら`content/works/{annictId}.json`に
1作品1ファイルで追記する運用にしている（声優・監督・製作会社・原作者名はAnnictから自動取得）。

**情報源の優先順位（一次情報のみ・Wikipediaは使わない）**:
- Wikipediaは一次情報ではないため使用しない（本ルールの`sourceUrl`＝一次情報という前提に反する）。
- **第1候補: 公式サイト**（Annictの`officialSiteUrl`）。あらすじ・見どころ・原作/出版社が明記されている。
- **第2候補: dアニメストアの作品ページ**。公式サイトがアクセス制限（403等）で取得できない場合の
  自動フォールバック。配信サービス自身が公開している紹介文なので一次情報として扱える。
  Claude単独で作品ページを特定できる（下記の手順で完全自動化可能）。
- **第3候補（ユーザー承認済み・2026-07-08導入）**: 公式サイト・dアニメどちらにも情報がない場合、
  `eiga.com`（映画.com）の「解説・あらすじ」欄、`animatetimes.com`（アニメイトタイムズ）の
  ニュース記事、配給・製作委員会構成企業の公式ニュースリリース等、**取材・配給元発の一次情報に
  近い媒体**も可とする。ただしWikipediaと二次創作まとめサイトは引き続き禁止。

**公式サイトであらすじが見当たらない時のチェックリスト（2026-07-08の教訓）**:
トップページだけで「記載なし」と判断せず、以下を順に試す。
1. **サイト内の個別ページを探す**: ナビゲーションに「物語」「STORY」「INTRODUCTION」
   「作品概要」「あらすじ」等のリンクがあれば、そのページを直接取得する
   （例: `/story/`, `/introduction/`, `/about`）。WebFetchでリンク一覧を聞くと見つかることが多い。
   ページ内アンカー（`#story`等）の場合は同一ページ内にセクションとして存在することがある。
2. **JS描画（SPA）で本文が取れない場合**は `https://r.jina.ai/<元URL>` を頭に付けて再取得する
   （レンダリング後のHTMLを読める）。個別ページにも同様に効く。
3. **ストーリー本文が画像で埋め込まれている**（`img_story01.webp`等）場合はテキスト抽出不可。
   これは「記載なし」ではなく「取得不可」として扱う。ユーザーがGoogleレンズ等でOCRしたテキストを
   提供してくれた場合はそれを一次情報として使ってよい（誤字・ふりがな混入等の明らかなOCRノイズは
   整形してよいが、固有名詞や内容を推測で補わない）。
4. **エピソード単位のあらすじしか無い**場合（シリーズ全体の紹介文が無く第1話あらすじのみ等）は、
   それを作品紹介として使ってよい。**ただし原則、1話の「事件・展開」そのものではなく、
   作品の設定・世界観・背景を説明している部分に限る**（例:「〇〇という島を舞台に、△△な主人公が
   □□という出来事に巻き込まれる」という導入部はOK。「第3話で敵が現れて〜」のような
   話数固有の細かい展開まで書かない）。
5. それでも見つからなければ、`eiga.com`・`animatetimes.com`等の第3候補を試す。
6. 未公開・今後内容が明らかになる作品（記念短編等）は無理に埋めず、
   情報公開後に追記する前提で今回は見送る。

**dアニメストアから作品ページを特定する手順（公式サイトが取れない時）**:
1. 検索REST APIを叩く（ログイン不要・JSONが返る）:
   `https://animestore.docomo.ne.jp/animestore/rest/WS000105?searchKey=<作品名をURLエンコード>&length=20&vodTypeList=svod_tvod`
   → 応答に `workId` と作品タイトルの一覧が入る。タイトル（シーズン数含む）が一致するものを選ぶ。
2. 作品ページを取得する:
   `https://animestore.docomo.ne.jp/animestore/ci_pc?workId=<workId>`
   → あらすじ・原作・制作会社が公開されている。これを`sourceUrl`にする。

**進め方（セッション単位・完全自動化はしない＝内容の正確性は人の目でも確認する）**:
1. ユーザーが「続きをお願い」等と伝えたら、未整備の作品（`content/works/index.ts`の
   `WORK_DETAILS`に無いID）から目安15件を選ぶ。今期の注目度（`watchers`）が高い作品を優先する。
2. 上記の優先順位で一次情報を確認し、事実に基づいてあらすじ・見どころを要約する。
   **書いていない情報を創作しない**（CLAUDE.mdの「推測データで埋めない」方針と同じ）。
   著作権に配慮し、紹介文を丸写しせず要約する。出版社は一次情報に明記がある場合のみ記載し、
   アニメオリジナル作品や記載が無い場合は`publisher`を省略する。
3. `content/works/{annictId}.json` を作成し（`WorkDetailContent`型: synopsis / highlights /
   publisher? / faq? / sourceUrl）、`content/works/index.ts`の`WORK_DETAILS`に1行追記する。
   `sourceUrl`には実際に参照した一次情報のURL（公式サイトまたはdアニメの作品ページ）を必ず入れる。
4. 追記後は `npx tsc --noEmit` で型エラーが無いことを確認する。

**`faq`（よくある質問）の追記ルール（2026-07-27導入）**:
続編作品には「2期から見ても大丈夫？」「1期はどこで配信されている？」といった視聴前の疑問が
検索されるため、`faq: [{ question, answer }]` に人力で追記できるようにした。作品ページに
可視テキストとして出しつつ、FAQPage構造化データにも合流する（生成AIの回答に引用されうる形になる）。
- **全作品には付けない**。実測（GSC・Vercel Analytics）で需要が確認できた作品に絞る。
  109作品分を人力で維持する運用は続かないため、`content/sns/spotlight.js`と同じ考え方で
  「実測で需要がある作品だけ」に投資する。
- **回答は`sourceUrl`の一次情報で裏が取れる事実だけで書く**。あらすじ・見どころと同じ制約。
  「たぶん続きもの」のような推測は書かない。確認できないことは項目ごと省く。
- 数値（話数・巻数・配信サービス名）は原典の表記に合わせ、確認した日付を回答文に入れる
  （配信状況は変わるため。例:「2026-07-27時点」）。
- 実例: `content/works/14132.json`（逃げ上手の若君 第二期）。第一期／第二期のBlu-ray収録話数が
  第十二回→第十三回と通し番号で続いている、という公式サイトの記載を根拠にしている。

### AI独断解釈サムネ（2026-07-07導入）

作品カード・作品ページに出すサムネは、権利者の画像を使わず、Pollinations（無料・APIキー不要）で
**タイトルから連想した本作品と無関係な創作イラスト**を事前生成して `public/works/{annictId}.jpg` に
保存している（表示時コスト・キー・レート制限ゼロ）。必ず「本作品との関連性はありません」の注釈を表示する。

**増やす手順**:
1. `scripts/gen-thumbnails.js` の `PROMPTS` に `{ id, seed, prompt }` を追記する。
   - プロンプトは**実在キャラの再現を避け**、タイトルの字面から連想した抽象的な情景にする。
   - **作品ごとに画風（絵柄トーン）を変える**（例: 水彩・油彩・浮世絵・フラットベクター・サイバーパンク等）。
2. `node scripts/gen-thumbnails.js` を実行（`public/works/` に保存し、`content/works/imageIds.ts` を自動更新）。
3. **生成画像を必ず人の目で確認**し、実在キャラに酷似していないか・不適切でないかをチェックしてからコミットする。
   気に入らなければ `seed` を変えて再生成する。

### レンタル作品の除外（2026-07-09導入）

dアニメストア・Amazonプライム等では、同じサービス内でも「見放題（サブスク内）」ではなく
「レンタル（都度課金）」扱いの作品がある。Annictにはこの区別を示すデータが無い
（`Channel`/`Program`型のスキーマを確認済み。チャンネル名だけでは判別不可）ため、
**人力で確認したものだけ** `content/works/rentalServices.ts` に追記する運用にしている。

- ここに載ったサービスは、カード一覧・カレンダー・配信サービス別対応本数・作品ページ本体の
  配信欄からは自動的に除外され、作品ページの「レンタル作品」という別枠に表示される
  （`lib/services.ts`の`splitRentalServices`が処理する）。
- **判定方法（最も効率的: 公式サイトの配信情報表を見る、2026-07-10改訂）**:
  多くの公式サイトは配信情報ページ（トップまたは`/onair/`等のサブページ）で
  「見放題」グループと「各話購入/都度課金/レンタル」グループを最初から分けて掲載している。
  **後者のグループにのみ排他的に載っているサービスだけ**をレンタル扱いにする。
  - **落とし穴**: バンダイチャンネル・Prime Videoは「見放題」グループと「各話購入」グループの
    **両方に同時掲載**されることが多い（見放題プラン加入者は無料、未加入者は都度課金という
    同一サービス内の料金差を表しているだけ）。両方に載っている場合はレンタル扱いにしない。
    片方（各話購入側）にしか載っていない場合のみ追加する。
  - **ニコニコの注意**: Annict側で「ニコニコ生放送」（無料同時配信）と「ニコニコチャンネル」
    （有料/都度課金の見逃し配信）が別チャンネル名で来ることがあり、本サイトの分類では
    どちらも同じ`niconico`キーに合流する。「ニコニコ生放送」の有無では判定しない
    （生放送ありでも公式サイトでは都度課金のみ、というメビウス・ダスト等の反例があるため）。
    公式サイトの配信情報表で「ニコニコ」関連の表記が「見放題」グループに一切現れず、
    「都度課金/レンタル」グループにのみ載っている場合だけレンタル扱いにする。
  - 上記が確認できない場合の代替手段として、対象サービス（dアニメストア・Amazonプライム等）の
    実際の作品ページで「レンタル」「都度課金」「ポイント」等の表記を確認する方法もある
    （dアニメストアは検索REST APIの`vodType`でも確認可）。
  - いずれの方法でも判定できなければ追加しない（配信情報と同じ「わからなければ空欄」の方針）。
- **追記手順**:
  1. `content/works/rentalServices.ts` の `RENTAL_SERVICES` に
     `{ annictId: ["service_key", ...] }` を追記する（service keyは`lib/services.ts`の`SERVICES`参照）。
  2. `npx tsc --noEmit` で型エラーが無いことを確認する。
  3. 対象作品のカード（トップページ）と作品ページ（`/anime/{id}`）で、レンタル対象サービスが
     配信チップから消え「レンタル作品」欄に表示されることを目視確認する。

## ⑦ 毎日ダイジェスト（フォロワー獲得施策・2026-07-05導入 / 2026-07-08に毎日化）

`.github/workflows/daily-digest.yml` が**1時間おきに起動し、投稿の時間帯に入っていれば**
その日の曜日に応じたダイジェストを生成して投稿する（`scripts/lib/build-digest.js`。
デプロイ済みサイトの `/api/season` を叩くだけで、ANNICT_TOKENの複製は不要）。

**曜日ごとの投稿内容（ネタの出し分け）**:
- **日曜**: 今期の注目作TOP5（1投稿）＋その日に放送・配信のある今期アニメがあれば曜日紹介（2投稿目）
- **月〜土**: その曜日に放送・配信のある今期アニメ（`broadcastWeekday`で抽出、注目度順に字数上限まで）。
  該当作品が無ければTOP5にフォールバック（1投稿のみ）
- **毎日**: 【どこで見れる？】スポットライト（1投稿。`content/sns/spotlight.js`から日替わり）
- 本文の長さは投稿先ごと（`PLATFORM_MAX_LEN`）。X/Blueskyは260字（X280字・Bluesky300字に
  安全に収まる）、Mastodon/Threadsは440字（どちらも上限500字）。

**投稿先ごとに本文を書き分ける（2026-08-06導入）**: 下の⑦-13を参照。
Bluesky / Mastodon / Threads で1行目・締め・問いかけが変わり、同じ曜日でも週替わりで
言い回しが変わる（乱数ではなくJSTの日付から決まる＝同じ日なら何度実行しても同じ本文）。

**投稿時間の出し分け（2026-08-05導入）**: 上の内容を1度に連投せず、種類ごとに時間帯を分ける。
7〜10時＝注目作TOP5 / 11〜12時＝【どこで見れる？】/ 18〜21時＝その曜日の放送・配信。
**ただしMastodonだけは従来どおり1日1回・5〜7時台にその日の分をまとめて投稿する**
（時間帯で分けるのはBluesky/Threadsのみ。2026-08-05に利用者の指定で元の運用へ戻し、
2026-08-06に時間帯を21〜23時台から5〜7時台へ変更＝これも利用者の指定）。
該当が無い枠はその日は投稿0件（平日の朝など）。GitHub Actionsのscheduleは数時間平気で
遅れるので、**予定時刻に1回起動するのではなく1時間おきに起動して「いまがどの時間帯か」を
自分で判定する**方式にしてある。仕組みと経緯は下の⑦-9。

> 2026-07-08まではファイル名`weekly-digest.yml`・週1（月曜のみ）だった。毎日化に伴い
> `daily-digest.yml`にリネームし、cronを`0 12 * * 1`→`0 12 * * *`に変更した。
> さらに2026-08-05に、1日1回（21:00 JST）から時間帯3枠に分け、cronは毎時起動
> （`41 * * * *`）1本にした。

**サイト実画面のスクリーンショット添付（2026-07-14導入）**: Bluesky・Mastodonへの投稿には、
その曜日のカレンダー画面（`?view=calendar&day=火`等）または「今期の注目作TOP5」パネルを
開いた画面（`?ranking=open`）を、Playwrightのヘッドレスブラウザで撮ってそのまま添付する
（`scripts/lib/capture-screenshot.js`）。新規デザインの画像は作らず、サイトの実画面をそのまま
使う方針。カレンダー表示・曜日選択・TOP5パネルの開閉はURLクエリで直接復元できる
（`components/SeasonExplorer.tsx`）。放送作品が0件の曜日はカレンダー画像を付けない
（TOP5フォールバック時はTOP5画像になる）。スクリーンショット取得に失敗しても投稿自体は
画像なしで続行する（`post-bluesky.js`/`post-mastodon.js`）。**X（下書きIssue）には画像を
添付しない**（手動投稿時に手元でスクリーンショットを撮って添付する運用のまま）。**Threads
（2026-07-22導入）はこのスクリーンショットを使えない**（後述の理由。2026-07-27から
サイト側の公開画像エンドポイントで別途画像を添付している）。

- **Bluesky・Mastodon・Threads**: 投稿APIが無料のため**自動投稿**する。Secrets未設定の間は
  「未設定のためスキップ」とログを出すだけで、ワークフロー自体は失敗にならない。
  3つのステップは互いに独立していて、1つが失敗しても残りは実行される（`if: !cancelled()`）。
  どれかが失敗した日は「SNS自動投稿が失敗しています」Issueが立つ（経緯は⑦-8）。
  **Threadsだけ画像の渡し方が違う**: ThreadsのIMAGE投稿は公開URLの`image_url`が必須で、
  Playwrightで撮ったPNGバイナリを直接アップロードできない（`post-threads.js`冒頭コメント参照）。
  そのため導入時（2026-07-22）はテキストのみだったが、2026-07-27にサイト側へ公開画像
  エンドポイント（`app/api/sns-image`）を用意し、そのURLを渡す形で画像付きになった。
  画像の取得に失敗した場合はテキストのみで投稿する（本文中の最初のURLが自動でリンク
  プレビューカードになる＝Threads公式仕様なので、画像なしでも導線は保たれる）。
- **X**: 2026年2月の料金改定でAPI投稿が有料（1件$0.015〜$0.20）になったため
  自動投稿はしない。代わりに同じ下書き文を**GitHub Issueとして自動起票**するので、
  中身を確認してブラウザ/アプリから手動でコピペ投稿する。

### 有効化する場合に必要なSecrets（任意・未設定でも動く）
| サービス | Secret名 | 取得方法 |
|---|---|---|
| Bluesky | `BLUESKY_IDENTIFIER` | ハンドル名（例: `animedia.bsky.social`） |
| Bluesky | `BLUESKY_APP_PASSWORD` | Bluesky設定 → プライバシーとセキュリティ → アプリパスワード（**通常のログインパスワードではない**） |
| Mastodon | `MASTODON_INSTANCE_URL` | 登録したインスタンスURL（例: `https://mstdn.jp`） |
| Mastodon | `MASTODON_ACCESS_TOKEN` | インスタンスの 設定 → 開発 → 新規アプリ作成 → スコープに**`write:statuses`と`write:media`の両方**を付けたトークン |
| Threads | `THREADS_ACCESS_TOKEN` | 長期アクセストークン（60日有効）。取得手順は`docs/threads-setup.md` |
| Threads | `GH_SECRETS_PAT` | トークン自動延長用のGitHub fine-grained PAT（対象リポジトリのSecrets: Read and write）。未設定だと60日ごとに手動で再発行が必要 |

いずれも**無料アカウント・無料の範囲**で取得できる（Xのような従量課金は発生しない）。
Secretsは日次ダイジェスト・新シーズン告知の両ワークフローで共有される（同じ名前を1回登録すれば両方効く）。

> **既知の落とし穴（2026-07-17確認）**: `write:statuses`（投稿）だけのスコープでトークンを
> 作ると、本文投稿は成功するのに画像添付（`POST /api/v2/media`）だけ
> `403 This action is outside the authorized scopes` で失敗する。エラーはログに出るだけで
> ワークフロー自体は成功扱いになるため気づきにくい（`post-mastodon.js`が画像添付失敗時は
> 画像なしで投稿を続行する仕様のため）。**`write:media`スコープを追加してトークンを
> 再発行し、GitHub Secretsの`MASTODON_ACCESS_TOKEN`を更新すれば直る**（コード側の不具合ではない）。

### やること（都度・目安2〜3週に1回）

1. Claude に「配信の需要シグナル/流入リードを集めて」と依頼する。

  （放送開始前の誤誘導を避ける方針=CLAUDE.mdの「放送開始1週間前ルール」と同じ考え方）。

### 効果の見方（`?ref=`で実測する）

返信下書きのリンクには `?ref=chiebukuro` のように媒体名が自動で付く。これを消さずに貼ると、
Vercel Analyticsの参照元（リファラー）で「実際にそのリンクから来た人」が数字で確認できる。
2〜3週分たまったら実際の流入数を見て、効果があるかを判断する。

### 今後（検証がうまくいった場合）

知恵袋は届く人数自体は少ない（外部リンクがnofollow・1回答1本までの制約があるため）。本命は
同じ仕組みをX向けに転用し、⑫の「リーチ」枠を今の検索クエリ配布から「この返信案付きリード一覧」に
差し替えること。Xは到達量が知恵袋より桁違いに大きいため、効果が出ればそちらへ主軸を移す。

**詳しい技術仕様（オプション一覧・分類ロジック・既知の限界）は
[`docs/demand-scan.md`](./demand-scan.md) を参照。**

## ⑦-3 表示速度の改善（パフォーマンス対策・2026-07-09導入）

**背景**: `/api/season`はAnnictへの問い合わせ結果を10分キャッシュしている
（`lib/annict.ts`の`next.revalidate: 600`）。以前はトップページ（`/`）がSPA構成で
クライアント側からこのAPIを叩く実装だったため、**キャッシュが切れた直後に訪問した人**は
Annictへの生取得を直接待たされていた（実測**7〜8秒**、カーソルページネーションで
複数ページを直列に取得するため、Annict側の応答時間が積み上がっていた）。

**対策（3本立て）**:

1. **クエリの軽量化**（`lib/annict.ts`）: シーズン一覧クエリの`programs`上限を
   500→300件、`staffs`上限を40→15件に削減（作品個別ページ用のクエリは完全性を
   優先しそのまま）。さらに1リクエストあたりの取得件数を50→250件に増やし、
   通常シーズンなら1リクエストで完結するようにした（以前は4ページ×約1.6秒=6.4秒が
   支配的要因だった）。実測: コールドでも2〜4秒程度まで短縮（作品数次第）。
   programsの追いページング（放送局が多い一部作品のみ発生）も直列→並列
   （`Promise.all`）に変更済み。
2. **トップページのSSR化**（`app/page.tsx`）: 以前は完全クライアント側フェッチの
   SPA（"use client"）で、マウント後に`/api/season`を叩いてから描画していたため、
   白画面での待ちが発生していた。`/season/[year]/[season]`と同じ要領でサーバー側
   に先にデータ取得させ、`initialData`としてHTMLに含めて返すように変更。
   年・シーズンの解決ロジック（URLクエリ`?year=&season=`から今どのシーズンを
   見るか決める処理）はサーバー・クライアントで完全に一致させる必要があるため、
   `lib/resolveSeasonParams.ts`に共通関数として切り出し、`app/page.tsx`と
   `components/SeasonExplorer.tsx`の両方から呼ぶようにした。
3. **キャッシュ温め**（`.github/workflows/warm-cache.yml`）: **5分おき**に本番サイトの
   今年分を叩いて温める。対象は6種類（2026-07-15に②③、2026-07-24に④⑤、
   2026-07-27に⑥を追加）:
   ① `/api/season` … トップのSPAが季節タブ切替でクライアント側から叩くAPI（データ
      キャッシュ＋API関数を温める）。
   ② `/season/{year}/{season}` … ISR化したSSRシーズンページ（下記⑦-5）。叩くと
      ページHTMLがCDNエッジに載り、以後の実訪問者は関数を実行せず
      `X-Vercel-Cache: HIT`（実測0.01〜0.1秒）を引く。
   ③ `/` … トップページ。2026-07-21にISR化（`searchParams`依存を外し
      `revalidate=900`）したので、②と同じくページHTMLがエッジに載る。
   ④⑤ `/rankings/{year}/{season}`・`/exclusive/{year}/{season}` … **現在クールのみ**。
      ランキング/独占配信の需要は今期に集中するため4シーズン全部は温めない。
   ⑥ `/anime/{id}` … 作品個別ページ。**現在クールの注目度（watchers）上位60件**。
      件数はワークフロー内の`WORK_LIMIT`1行で変えられる。
   - GitHub Actionsの`schedule`は最短間隔が保証されない。**実際は高負荷時に間引かれ、
     3〜9時間毎になることが判明している**（2026-07-24確認）。表示速度の本線は
     ISR（`revalidate`）自体であり、この温めはあくまで補助（コールドを引く確率を
     下げるだけで、無くても致命的ではない）と理解した上で運用する。
   - **今年の温めのみ**。過去年は下記⑦-4のスナップショット方式＋ISRで既に常時速い
     ため対象外（過去年をライブ取得で温める`warm-cache-past-years.yml`は撤去済み）。
   - 追加費用・追加インフラは不要（既存のGitHub Actions無料枠内）。
   - **手動実行（動作確認用）**: GitHub Actionsの画面からワークフローを手動実行できます。
     新デプロイ直後や間隔をずらしたいときに使います。
     
     > 1. https://github.com/junatushi/animedia/actions
     > 2. 左サイドバーから「キャッシュ温め（今年分）」（`warm-cache.yml`）をクリック
     > 3. 右上「Run workflow」ボタン → 「Run workflow」で確認・実行
     > 4. 「温め対象: 60 件」「完了（200以外: 0 件）」が出れば正常（失敗時は各ステップのログを確認）
     > 
     > ⑥ステップ（作品ページの温め）で `jq` のエラーが出た場合は、
     > GitHub Actions実行環境の`jq`版の差分（配列スライスと`limit`の互換性）が疑わしいため、
     > `jq --version` を確認した上で`.github/workflows/warm-cache.yml`の该当行を調整。

## ⑦-4 過去年のスナップショット固定（パフォーマンス対策・2026-07-15導入）

**背景**: 過去年（今年より前）は当初、ライブ取得＋Vercelデータキャッシュ（24時間）＋
毎日の温めCron（`warm-cache-past-years.yml`）で速くしようとしていた。しかし
**Vercelのデータキャッシュは温めが成功した翌日でもエントリが追い出される**ため、
過去年の初回アクセスがコールドを踏み続けていた（2026-07-15計測: 前日の温めCron成功後も
**2024夏9.4秒・2020冬5.1秒**）。1日1回の温めでは64通り（2010〜昨年×4季節）を追い出しから
守りきれず、方式として破綻していた。

**対策**: 過去のクールは放送終了済みで配信情報がほぼ動かないため、確定値を
**リポジトリ同梱のスナップショット**（`content/snapshots/{year}-{season}.json`）に固定し、
`lib/getSeasonData.ts`が過去年はそれを即返す。キャッシュ追い出しの影響を受けず、
Annict通信ゼロで**常時0.03秒程度**（トップページSPAの`/api/season`・SSRシーズンページ
両方に効く）。webpackが各シーズンを個別チャンクに分割するのでバンドルは肥大しない。
スナップショットが無い過去年は従来のライブ取得＋24時間キャッシュへ自動フォールバックする。

- **生成**: `node scripts/snapshot-past-seasons.ts [fromYear] [toYear] [--force]`。
  引数省略で2010〜昨年の全過去年を生成（既存ファイルはスキップ、`--force`で上書き）。
  `ANNICT_TOKEN`が要る（`.env.local`から読む）。
- **年またぎ時の手当て（重要）**: 年が変わると「昨年」が新たに過去年になる。その分の
  スナップショットが無いとライブ取得フォールバック（コールド初回が遅い）になるため、
  年明けに `node scripts/snapshot-past-seasons.ts <前年> <前年>` を1回実行して固定する。
  例: 2027年になったら `node scripts/snapshot-past-seasons.ts 2026 2026`。
- **配信情報を後から反映したいとき**: 過去クールにAnnict側で配信が追加された等で
  更新したい場合は `--force` で該当年を取り直す（例:
  `node scripts/snapshot-past-seasons.ts 2024 2024 --force`）。通常は不要。
- 追加費用・追加インフラは不要（静的JSONをコミットするだけ）。

## ⑦-5 シーズンページのISR化（パフォーマンス対策・2026-07-15導入）

**背景**: 全ページが`X-Vercel-Cache: MISS`／`Cache-Control: no-store`を返していた
（実測2026-07-15）。つまりトップ`/`もシーズンページも**リクエストのたびに毎回サーバー
関数を実行**してHTMLを描画しており、⑦-3の温めが叩いていたのは`/api/season`（データ
キャッシュ＋API関数）だけで、**ページの描画関数自体は温まっていなかった**。そのため
関数がコールドの時に主要入口へ来た訪問者が2秒級の初回を踏んでいた（実測:
`/season/2026/autumn`が一度2.3秒、温まると0.4秒）。原因は動的セグメント
`[year]/[season]`に`generateStaticParams`が無く、`revalidate`を付けても動的
レンダリングのままCDNキャッシュされないNext.js 14の挙動。

**対策**: `app/season/[year]/[season]/page.tsx`に`export const revalidate = 600`と
`generateStaticParams`（今年の4シーズンを列挙）を追加してISR化した。ビルド出力で
`● (SSG)`となり、`Cache-Control: s-maxage=600, stale-while-revalidate`／
`x-nextjs-cache: HIT`でCDNエッジから配信される（実測0.01〜0.1秒、関数実行なし＝
コールドなし）。ここに無い年（過去年など）も`dynamicParams`（既定true）で初回
オンデマンド生成→以後キャッシュ。データ鮮度は10分（⑦-3のデータキャッシュと同一）。

- **トップ`/`も2026-07-21にISR化した**（`revalidate=900`）。当初は`searchParams`
  （`?year=&season=`の共有リンク再現）をサーバー側で読む都合で動的レンダリングが
  強制されエッジキャッシュできなかったが、searchParams非依存にして常に今期を初期表示し、
  年・季節の切替やディープリンクの解決はクライアント側（`SeasonExplorer`）に寄せた。
- **middlewareとの関係**: `middleware.ts`が全リクエストでsupabaseセッションを更新するが、
  匿名ユーザー（大多数）は`Set-Cookie`が付かないためエッジキャッシュを阻害しない
  （ログインユーザーだけトークン更新でCookieが付き、その応答は個別化される＝正しい挙動）。
- **年またぎ時**: `generateStaticParams`はビルド時の西暦で今年4シーズンを決めるので、
  年が変わって再デプロイすれば自動で新しい今年が対象になる（手作業不要）。
- 追加費用・追加インフラは不要。

## ⑦-6 作品ページのISR化とカードのタップ領域（2026-07-27導入）

**背景**: 「スマホで『幼女戦記Ⅱ』をタップしても作品ページに進まない。ほかの作品も
遅いときがある」という報告から、別々の2つの問題が見つかった。

**問題A: カードのタップ領域がタイトルの文字だけだった**。カードから`/anime/{id}`へ
進めるのは`.card-title`内のリンクテキストのみで、タップ領域がタイトルの文字数に
比例していた。スマホ幅375pxでの実測は「幼女戦記Ⅱ」61×17px（カード面積の1.1%）、
「猫と竜」36×17px、「盗掘王」39×17px。Apple推奨44×44pt・Google推奨48×48dpを
大きく下回り、**今期132作品すべてが高さ17px**。短いタイトルほど「押しても何も
起きない」状態だった。

→ 対策: `app/globals.css`でタイトルのリンクを`::after`（`position:absolute; inset:0`）
でカード全面に引き伸ばす（stretched link）。リンク要素は増えないのでスクリーン
リーダー・検索エンジンから見た構造は変わらない。配信バッジ・公式サイト・右上の
操作ボタンだけを`z-index`で上に出して個別に押せるまま維持した（実測: カード面の
82%が作品ページへ、残りは意図したリンク・ボタン、死に領域0%）。カレンダー行・
クール横断検索の簡易カードにも同じ対応をした（カレンダー行は321×17px→321×114px）。

- **今後カード内にリンクを増やすときの注意**: 引き伸ばしたリンクより上に出すのは
  「リンク要素そのもの」だけにする。列や行ごと`z-index`を上げると、要素同士の隙間や
  ただのテキスト（「◯人が注目」など）がタップ領域から抜け落ちる。

**問題B: `/anime/[id]`が完全に動的だった**。`revalidate`未指定で毎リクエスト
サーバー描画しており、本番実測でも常に`x-vercel-cache: MISS`の0.42〜0.82秒
（Annictのデータキャッシュ切れ直後は数秒）。App Routerのクライアント遷移はこの間
まったく画面が変わらないため、問題Aと合わさって「押しても進まない」体感になっていた。

→ 対策: `app/anime/[id]/page.tsx`に`export const revalidate = 900`と
`generateStaticParams`（**空配列**）を追加。ローカル本番ビルド実測で初回0.81秒→
2回目以降0.010秒（`x-nextjs-cache: HIT`）。

- **`revalidate`だけでは効かない**。`generateStaticParams`が無いとルートが
  `prerender-manifest.json`に載らず動的のまま（ビルド出力が`ƒ`のまま）。空配列を
  返すと「ビルド時には1件も焼かないが、アクセスされたIDから順にISRキャッシュに
  載せる」構成になり、出力が`● (SSG)`に変わる。⑦-5のシーズンページと同じ理屈だが、
  作品は数千件あるのでビルド時に全部焼くのは現実的でない。
- **`loading.tsx`は置かない**。タップ直後に骨組みを出せて体感は良くなるが、
  ストリーミングでヘッダが先に確定するため`notFound()`が404ではなく**200
  （ソフト404）**で返るようになる（実測: `/anime/88888888`の`.meta`が`status:200`に
  なり、`loading.tsx`を消すと404に戻る）。存在しない作品IDが200で返るのは検索エンジンに
  対して有害なので採用しない。
- **温めはHTMLを叩くだけでよい**。カードのタップはHTMLではなくRSCペイロードを取りに
  行くが、ISRのキャッシュエントリはHTMLとRSCが1組で書かれるため、`/anime/{id}`を
  1回叩けばスマホのタップもHITになる（iPhone UAで実測0.010秒）。⑦-3の⑥がこれ。
- **PC/スマホで差は無い**。UAによる出し分けはコードのどこにも無く、ISRのキャッシュ
  エントリは共有される（iPhone UAで直接URL 0.009秒／タップ 0.010秒を実測）。
- **未対応（把握済み）**: ランキングページ（`/rankings/{year}/{season}`）の
  「先行配信ランキング」は`<ol>`内の文中リンクで、10本すべて高さ18px（「猫と竜」は
  40×18px）。後続に日付テキストが続く通常の本文リストなので行全体のリンク化は
  不自然と判断し、そのままにしている。行間を広げて44pxを確保する対応は可能。

## ⑦-7 配信バッジの中に別リンクを入れない（2026-07-28）

**背景**: 「『片田舎のおっさん、剣聖になるⅡ』の配信バッジにチェックマークがあり、
押すとPrimeではないページに飛ぶ」という報告。

**原因**: Annict未登録の配信情報を人力補完した作品（`content/works/extraServices.ts`）で、
出典（一次情報）へのリンクを**バッジの中に「✓」の小さなアンカー**として置いていた。
実測でチップ幅84pxのうち53pxがPrime Video（アフィリエイト）へのリンク、隣接する14pxが
GAME Watchの記事へのリンク。記号だけで何のリンクか伝わらず、間隔も空いていないため
「バッジを押したのに無関係な記事に飛んだ」となる。HTML的には入れ子ではなく兄弟要素
だったのでバリデーション上の問題は無く、見た目と遷移先の不一致が本質だった。

→ 対策: バッジ内のアンカーを廃止し、バッジ列の下に文章＋ラベル付きリンクの注記
（`.svc-manual-note`）として出す（「点線のバッジは…補完したものです（◯◯の出典記事 ↗）」）。
点線枠と`title`属性は残すので「手動確認」であることは従来どおり伝わる。カード一覧は
`hideManualNote`で注記を省き（作品ページに出典が出る）、空いた場所はカード全面の
stretched linkに戻る＝押すと作品ページに進む。

- **今後の原則（重大度高）**: 配信バッジの中に、バッジ本体と行き先の違うリンクを置かない。
  補足情報へのリンクはバッジ列の外に、何のリンクか分かる文言を付けて置く。記号だけの
  リンクにしない。バッジを押したら必ずその配信サービスに行く、を崩さない。
- **再発防止（機械的な検査）**: `node scripts/check.ts` に「バッジ列（`.svc-chips`）の中に
  現れる`href`は`pickAffiliate`/`officialUrl`由来の1つだけ」を固定する検査を入れた。
  出典リンクをバッジ内に戻すと即NGになる（実測: 戻すと `["s.manualSourceUrl","href"]` を
  検出して失敗）。構造を変えるときも検査を消さず、目印（`className="svc-chips"`〜
  `className="svc-manual-note"`）の方を更新すること。
- **「PR」タグは復活させない**: ステマ規制対応は`title`属性＋ページ下部の開示文で確定
  （2026-07-27廃止、2026-07-28に方針として確認）。事故が起きない限り再提案しない。
- 同時に見つかった小さな不具合: 人力補完サービスにアフィリエイトリンクが付いている場合、
  `title`属性が「（Annict未登録・公式情報で手動確認）」だけになり「（広告リンク）」が
  消えていた（三項演算子で手動確認を優先していたため）。両方を並記するよう修正した。
- あわせて`/privacy`の広告表記の記述を実装に合わせた（2026-07-27にPRタグを廃止済み
  なのに「広告リンクには『PR』の表示を付け」と書いたままだった）。

## ⑦-8 Threads自動投稿が断続的に止まっていた件（2026-08-04〜05）

**症状**: 毎日のダイジェストのうち**Threadsだけ**が投稿されない日があった。2026-07-22〜08-02の
約2週間で4回（7/22・7/23・7/29・8/2）。エラーはいずれも publish（`threads_publish`）が
`Media Not Found`（OAuthException code 24 / error_subcode 4279009）を返すもの。

**なぜ2週間気づかなかったか**（ここが本題）:
- 失敗はActionsの赤マークとGitHub既定のメール通知にしか出ず、日々の運用動線（毎日届く
  「Xへの投稿下書き」Issue）には現れなかった。**成功しても失敗しても下書きIssueは立つ**ので、
  Issue一覧を見ているだけでは異常に見えなかった。
- 7/24に一度「直した」つもりでいた（コンテナのstatusポーリング追加）ため、以後の失敗を
  疑わなくなっていた。実際には直りきっておらず7/29・8/2に再発している。

**原因は3つ**（`scripts/post-threads.js`）:
1. **statusポーリングに抜け道があった**。`GET /{creation-id}?fields=status` が `status` を
   返さない（undefined）ときに「待たずに公開へ進む」分岐が入っていた。スタブでの動作確認用の
   つもりだったが、本番APIが status を省いて返した場合にも効いてしまい、7/24の修正前と同じ
   「待たずにpublish」になっていた。**undefined は「公開してよい」ではなく「まだ分からない」**
   なので、IN_PROGRESS と同じ扱い（待ち続ける）に変えた。
   → 教訓: **スタブ用の抜け道を、本番でも通る分岐として書かない**。テストと本番で違う経路を
   通ると、テストでは絶対に出ない穴ができる。今回は「待ち時間の長さだけスタブで潰し、
   分岐はまったく同じものを通す」形に直した（`IS_STUB` は `wait()` の中だけで使う）。
2. **publishが一発勝負だった**。status=FINISHED を確認した直後でもThreads側の伝播待ちで
   Media Not Found が返ることがある。一時的なエラー（HTTP 429 / 5xx / subcode 4279009）に
   限り、5秒→10秒→20秒→30秒のバックオフで最大5回まで再試行するようにした。恒久的な
   エラー（トークン失効・本文不正など）は再試行しても同じなので即座に失敗させる。
3. **1件の失敗でその日が全滅していた**。投稿ループが throw で抜けるため、1本目が落ちると
   2本目（日曜のTOP5＋曜日紹介など）も投げられなかった。1件ずつ try/catch で独立させ、
   最後に「N件中M件失敗」でまとめて失敗を報告する形にした。**同じ形をしていた
   `post-bluesky.js`・`post-mastodon.js`も揃えた**（まだ事故は起きていないが、日曜は
   2件投稿するので同じ穴が空いていた）。

**再発防止**:
- **失敗に気づける化**（`daily-digest.yml`）: どれかのSNS投稿が失敗したら
  **「SNS自動投稿が失敗しています」というIssueを起票**する。毎日下書きIssueが立つ同じ場所に
  失敗も並ぶので、運用動線の中で目に入る。既に開いている同名Issueがあればコメントを足すだけに
  して、毎日積み上がらないようにしてある。直したらIssueを閉じる（次の失敗で新しく立つ）。
- **SNS投稿ステップを本当に独立させた**（`daily-digest.yml`）: 「できたものだけ出す」方針は
  2026-07-24にコメントで書かれていたが、実装は`if: !cancelled()`が**Xの下書き起票にしか
  付いていなかった**。そのためBlueskyが落ちるとMastodon・Threadsが丸ごとスキップされる
  状態だった（幸い発生していない）。Bluesky/Mastodon/Threadsの各ステップにも同じガードを付けた。
- **回帰テスト**（`node scripts/check-threads.js`）: Threads APIのスタブを立てて
  `post-threads.js`を実際に動かし、①statusが返らないコンテナで待たずに公開しないこと、
  ②一時的なMedia Not Foundから再試行で回復すること、③恒久的なエラーは再試行しないこと、
  を機械的に固定した。ネットワークには出ない（localhostのみ）。`scripts/check.ts`と同じく
  **この検査は消さないこと**。

## ⑦-9 投稿を時間帯で分け、同じ内容の連日投稿を止めた（2026-08-05）

**症状**: Bluesky/Mastodonの投稿内容が前日とまったく同じだった。

**原因**: **GitHub Actionsのscheduleは予定より数時間遅れて発火する**（このリポジトリの実測で
最大6.4時間）。旧cronは`0 12 * * *`＝21:00 JSTで、JSTの日付が変わるまで3時間しか余裕が
無かったため、遅延した実行が翌JST日にずれ込み、**2回の実行が同じJST日付を見て**本文が
完全一致した。実例:

| 実行 | 発火（UTC） | 発火（JST） | 起票されたIssue | 本文 |
|---|---|---|---|---|
| 8/3の枠 | 08-03 18:26 | **08-04 03:27** | #31（タイトルは8/3） | 【火曜】＋片田舎のおっさん |
| 8/4の枠 | 08-04 14:04 | **08-04 23:05** | #32（タイトルは8/4） | 【火曜】＋片田舎のおっさん |

注目人数（1,151→1,155）以外は1文字も違わない。Issueのタイトルだけが違って見えたのは、
**タイトルはランナーのUTC日付・本文はJST日付**という別々の基準で作っていたため（これも直した）。

**対策1: 投稿を3つの時間帯に分けた**（ユーザー要望でもある）。1日分をまとめて連投せず、
内容の種類ごとに時間帯を分ける。

| 枠 | 時間帯（JST） | 内容（kind） | 出る日 | 対象 |
|---|---|---|---|---|
| morning | 7〜10時 | 注目作TOP5（`top5`） | 日曜（＋放送作品が無い日のフォールバック） | Bluesky / Threads |
| noon | **11〜12時** | 【どこで見れる？】スポットライト（`spotlight`） | 毎日 | Bluesky / Threads |
| evening | 18〜21時 | その曜日の放送・配信（`airing`） | 放送作品がある日 | Bluesky / Threads |
| **mastodon** | **21〜23時** | **その日の全投稿をまとめて** | **毎日** | **Mastodon のみ** |

該当が無い枠は投稿0件で正常終了する（平日の朝、放送が無い日の夜など）。

**スポットライトを11〜12時にした経緯（2026-08-05）**: 当初は12〜14時にしていたが、
昼休みに見られる**12時台に確実に届かせたい**という判断で1時間手前にずらした。
12時開始だと、GitHubの間引き（起動間隔の中央値2.5時間）で13時台・14時台に投稿されて
昼のピークを外すことが多いため。
morningはnoonと重ならない範囲でできるだけ広く取り**7〜10時**としてある（枠同士は
重ねられない。重なると`slotForNow`の結果が定義順に依存して不安定になる）。朝は窓が
広いほど「間引きで丸ごと逃す」確率が下がるため、noonを前倒しした分だけ手前に広げた。

**Mastodonだけ従来方式に戻した経緯（2026-08-05）**: 時間帯で分けるのはBluesky/Threadsだけに
して、Mastodonは元の「1日1回まとめて」に戻した（利用者の指定）。実装は`BATCH_SLOTS`で、
`SLOTS`と違い**`kinds`を持たない**＝内容を絞らないのが違い。時間帯の考え方（開始時刻で
基準日を固定する／その日のうちなら遅れても出す）は共通なので、時間帯を逃しても日付が
変わるまでは投稿できる。

**Mastodonの時間帯を5〜7時台にした（2026-08-06・利用者の指定）**: 朝いちばんに「今日は
何が観られるか」を出す形になり、内容（その日の放送・配信）とも噛み合う。副次的な利点として
**JSTの日付が変わるまでの余裕が3時間から19時間に延びる**。scheduleの実測遅延は最大6.4時間
あり、21時起点は遅延がそのまま日付またぎになりうる位置だった（`anchorToSlotDate`が
前日分の投稿を防ぐので事故にはならないが、その日の投稿が丸ごと消える）。5時起点なら
遅延しても同じJST日の中に収まるので、取りこぼし自体が起きにくい。
注意点として、遅れ投稿を許す窓も3時間（21〜24時）から19時間（5〜24時）に広がる。
内容が「その日の放送・配信」でJST日付が変わらない限り古くならないため意図した挙動。
深夜0〜4時台が`false`（日付をまたいだ遅延実行を前日分として投げ直さない）ことは
`node scripts/check.ts`が固定している。二重投稿の防止も専用のキャッシュキー
（`posted-mastodon-<JST日付>`）で独立させてあり、片方が失敗しても、もう片方の再試行は
止まらない。

**対策2: 「予定時刻に1回起動」をやめた**（ここが肝）。当初はcronを3本（9時/12時/20時）に
分けたが、それでは**投稿時刻をまったく守れない**。旧構成`0 12 * * *`の実測遅延は
2.1〜6.4時間・中央値約5時間で、20時のつもりが翌1時になる。cronに何時と書いても無駄だった。

そこで**1時間おき（`41 * * * *`）に起動し、起動のたびに「いまがどの枠の時間帯か」を
自分で判定して、その枠がまだ未投稿ならそこで投稿する**方式にした。何時間遅延しても、
次の起動が時間帯の中に入りさえすれば狙った時間帯に投稿できる。

- 枠の判定は`scripts/current-slot.js`（中身は`build-digest.js`の`slotForNow`）。
  時間帯に入っていない起動は`npm ci`もPlaywrightのインストールもせず数秒で終わる。
- **二重投稿の防止**: 「枠＋JSTの日付」をキーにしたGitHub Actionsのキャッシュを、投稿できた
  後に保存する。次の起動はそれを見て「この枠は今日もう投げた」と分かる。
- **自動リトライ**: 全滅した回はキャッシュを残さないので、同じ時間帯の次の起動（1時間後）が
  自動で再試行になる。時間帯の幅（3〜4時間）がそのまま再試行の猶予になっている。
- **遅れ投稿**: 時間帯を丸ごと逃した日は、**その日のうち（JSTの同じ日）なら時間帯を過ぎても
  投げる**（`dueSlots`）。1回の起動で投げるのは1枠だけで、残りは次の起動が拾う。
- **手で投稿した日の抑止（`mark_only`）**: Actions → 毎日ダイジェスト → Run workflow で
  **mark_only にチェック**を入れて実行すると、投稿はせず「今日はもう投稿した」印だけを
  全枠＋Mastodonに付ける。臨時に手動投稿した日や、障害対応で二重投稿を避けたい日に使う。

### GitHubはscheduleをどれだけ間引くか（2026-08-05実測）

「1時間おきに起動する」と書いても、実際にはその通りには起動しない。同じリポジトリの
`warm-cache.yml`（当時`*/5 * * * *`＝5分おき指定）の直近87時間を数えた結果:

| | 値 |
|---|---|
| 本来の起動回数 | 1,046回 |
| **実際の起動回数** | **30回**（約97%が間引かれた） |
| 実際の起動間隔 中央値 | 2.5時間 |
| 最大の空き | 13.0時間（次点 8.3時間） |
| 4時間以上あいた回数 | 29回中4回 |

この分布から、**18〜21時の4時間枠を丸ごと逃す確率はおよそ16%（約6日に1日）**。
一方で**1日1回のcronは15日連続で1度も落ちていない**（遅れるだけ）。
つまりGitHubは「高頻度のcronを間引き、低頻度のものは確実に届ける」挙動をする。
どちらも単独では時間帯を保証できないため、上の「遅れ投稿」で取りこぼしを拾う。

あわせて`warm-cache.yml`を5分おき→1時間おきに落とした（2026-08-05）。実効の起動間隔は
既に3時間おき程度で変わらないのに待ち行列だけを積み上げており、同じリポジトリの他の
scheduleの間引きを悪化させていたため。効果は1〜2週間の実測で確認する。

**対策3: 投稿内容の基準日を枠に固定した**（`anchorToSlotDate`）。実行が予定より**早く**
始まることはないので、**いまのJST時刻がその枠の開始時刻より前なら、日付をまたいで遅延した
実行＝前日の枠**と確定できる。時間帯判定と二重で効かせている保険。

> **時間帯の定義はワークフローのYAMLに書かない。** `scripts/lib/build-digest.js`の`SLOTS`が
> 唯一の情報源で、YAMLは`node scripts/current-slot.js`に聞くだけ。両方に時刻を書くと、
> ズレたときに「投稿されない」「違う日の内容が出る」という気づきにくい壊れ方をする。
> `node scripts/check.ts`が「YAMLに投稿時刻がハードコードされていないこと」「cronが毎時
> 起動1本であること」を検査しているので、逆戻りしたら気づける（この検査を消さないこと）。

**あわせて直したもの**:
- Xの下書きIssueのタイトルをJST基準にした（従来はランナーのUTC）。
- Xの下書きIssueは**朝の枠でだけ1日分をまとめて起票**する（枠ごとに3件立てない）。
- 各SNS投稿ステップをXの下書き生成の成否から切り離した（`post-*.js`は自前で本文を
  組み立てるので、下書き生成が朝の枠にしか無くても投稿はできる）。

- トップページ（"/"）は従来どおりクライアント描画のまま（ディープリンクの解決に
  `useSearchParams` が要る／canonicalは "/" でキーワードを狙っていない／スクリーン
  ショット撮影の初期状態復元を壊さない、の3点から現状維持を選んだ）。
- `node scripts/check.ts` に「`SeasonExplorer` が `useSearchParams` をimportしない」
  「シーズンページは `SeasonExplorer` を直接使う」の機械検査を追加。

## ⑦-12 過去クール作品ページがAnnict障害でnoindexに戻る問題を修正（2026-08-06）

### 症状・懸念

スナップショット（`content/archive/index.json`に載っている1,961件のどれか）に

- 声優・監督・製作会社・原作者（`credits`）はスナップショットに無いため、
  推測で埋めずに空のまま返す（CLAUDE.mdの「推測で埋めない」方針どおり）。

- 判定は`content/archive/index.json`（既存。sitemap用に生成済み）から
  作品ID→スナップショットファイル名の逆引きマップを1回だけ作って使う。新しい
  索引ファイルは増やしていない。
- フォールバックが使われるのは「Annictが本当に落ちている/遅い」ときだけで、
  平常時は従来どおりAnnictからのライブ取得（フルの`credits`つき）を優先する。
- 対象は過去クールの**配信1件以上**の1,961件のみ（sitemapの対象と一致）。
  配信0件の過去作品・今期の作品は従来どおりで、この変更による挙動変化は無い
  （フォールバック対象外＝今まで通りエラー画面＋noindex）。

### 実測（ローカル本番ビルド、`ANNICT_TOKEN`をダミー値にして意図的にAnnictへの
ライブ取得を失敗させ、`curl`で確認。詳細は本セッションの最終報告を参照）

### 何が問題だったか

1. Bluesky / Mastodon / Threads が**完全に同一の本文**（Threadsのタグ数調整だけが差分）。
   同じ文面を3か所へ配るのはクロスポストでしかなく、どのSNSでも「よそで見た」扱いになる。
2. 曜日固定の番組表なので、**毎週ほぼ一字一句同じ投稿**がリピーターのタイムラインに流れる。
3. 告知型が100%で、返信・引用を誘発する要素が無い。会話が起きないのでリーチが伸びない。

### どう直したか（すべて `scripts/lib/build-digest.js`）
`buildPost(now, platform)` の第2引数で投稿先を受け取り、各 `post-*.js` が自分の投稿先を
渡す（`post-bluesky.js` → `"bluesky"` など）。省略時は `"x"`＝Xの手動投稿用の下書きで、
**従来どおりの文面のまま**（Xは人が手を入れて投稿する前提で、`docs/sns-templates.md`の
見本との対応も崩したくないため）。

- **投稿先ごとの言い回し**（`AIRING_LEAD` / `TOP5_LEAD` / `SPOTLIGHT_BODY` / `CALENDAR_CTA`）。
  **Mastodonは5〜7時台に1日分をまとめて出す枠**（`BATCH_SLOTS`）なので、
  「おはようございます。今日（8/6・木）放送・配信がある今期アニメは8本です。」のように
  **その日の全体像**から入る。Bluesky/Threadsは時間帯ごとに内容が絞られているので、
  その枠に合う短い導入にする。
- **本文の上限も投稿先ごと**（`PLATFORM_MAX_LEN`）。X/Bluesky=260字、
  Mastodon/Threads=440字（どちらも上限500字）。Mastodonの朝のまとめは作品を多く載せられる。
- **週替わりのバリエーション**。同じ曜日・同じ作品でも週が変われば言い回しが変わる。
- **問いかけ**（`QUESTION`）を枠ごとに絞って入れる。
  airing＝水曜と土曜（週2回）／spotlight＝隔週／top5＝3週に1回。Xには入れない。

### 守っていること
- **乱数は使わない**。`Math.random()` で毎回変えると、再実行・リトライのたびに本文が変わり
  「二重投稿か」「dry_runで見た本文と同じものが出たか」を判別できなくなる。
  GitHub Actions は間引き・遅れ投稿で同じ枠を複数回起動しうる（⑦-9）。
  バリエーションの入力は**JSTの日付だけ**（通し週番号 `weekIndex`）。
- **作品の評価は書かない**。埋め込む変数は事実だけ（曜日・本数・年・季節・作品名・
  配信サービス名・注目人数）。問いかけも「どこで観ているか」「何を追いかけているか」
  「配信情報の抜け」＝サイトの守備範囲の中だけにする。
- **Threadsのタグ1個制限**（`toSingleHashtagText`）はそのまま。本文の末尾行は必ず
  ハッシュタグだけの行にして、問いかけはURLより前に置く（末尾に置くと削られる対象がズレる）。

### ハマった落とし穴（同じ設計をするときの注意）
**「出す頻度」と「言い回しの回転」に同じ数を使うと、位相が固定されて毎回同じ文になる。**
最初の実装ではスポットライトの問いかけを「隔週（週番号が偶数）」で出し、文面も週番号で
回していた。登場日が必ず偶数週なので `週番号 % 2` が常に同じ値になり、**4回連続で
まったく同じ問いかけ**が出た。日付（経過日数）で回しても、登場間隔が14日なので同じ結果。
`QUESTION_RULE` は `due`（その日に出すか）と `seq`（**何回目の登場か**）を分けて持ち、
回転には `seq` を使う。`airing` の `seq` が `w * 2 + (水曜 ? 1 : 0)` なのは、通し週番号が
1970-01-01（木）起点＝1週が木〜水で、**同じ週の中では土曜が先・水曜が後**に来るため。

### 自前の効果測定ダッシュボード（`/admin/analytics`・2026-07-13導入）

Vercel Proに課金せず、既に導入済みのSupabase（無料枠のPostgres）へ同じイベントを自前で記録し、
`/admin/analytics?token=...`で直近30日の集計を見られるようにした。追加費用ゼロ。

**未設定の間の挙動**: `analytics_events`テーブルが無い・`ADMIN_DASHBOARD_TOKEN`が未設定の間は、
既存の`watched`/`notify`機能と同じ設計思想で「静かにスキップ」する（計測が失敗してもユーザー操作
自体は壊れない）。ダッシュボードは`ADMIN_DASHBOARD_TOKEN`未設定なら「未設定です」と表示するだけ。

**有効化手順**:
1. Supabaseダッシュボードの **SQL Editor** で以下を実行（`docs/supabase-setup.md`の手順6と同じ場所）:
   ```sql
   create table if not exists public.analytics_events (
     id bigint generated always as identity primary key,
     event_name text not null,
     event_data jsonb,
     created_at timestamptz not null default now()
   );

   alter table public.analytics_events enable row level security;
   -- ポリシーは意図的に1つも作らない（anon/authenticatedからは読み書き不可。
   -- service_role（RLSを無視する）経由の /api/track・/admin/analytics からのみ操作する）。
   ```
2. `.env.local`（および本番Vercelの環境変数）に `ADMIN_DASHBOARD_TOKEN` を追加する
   （任意の推測されにくい文字列。パスワード相当なので、コミットや共有はしない）。
3. `/admin/analytics?token=<設定した値>` にアクセスして確認する。トークン不一致・未指定は
   404（存在しないページと同じ扱い。不一致の理由は教えない）。
4. `robots.txt`で`/admin`はクロール除外済み、ページ自体にも`noindex`を設定済み。

**記録している内容**: `event_name`（`share_site`等、コード側でホワイトリスト済みの8種のみ）と
`event_data`（`service`名等の付随情報）のみ。IPアドレス・Cookie・ユーザーIDは一切記録しない。

これらは「どの作品・どのサービスに関心が集まるか」を早期に掴むための土台。
広告を検討する際の入稿ターゲット（訴求する作品・サービス）の根拠に使う。

## ⑭ CI（PRのゲート・2026-08-06導入）

`.github/workflows/ci.yml` が**PRの作成・更新時と、mainへのpush時**に自動実行し、
「コミット前の定番チェック」（`docs/handoff.md`末尾）と同じ4つを回す。

1. `npx tsc --noEmit`
2. `node scripts/check.ts` … 不変条件の検査
3. `node scripts/check-threads.js` … Threads投稿のスタブ検査
4. `npm run build` … 本番ビルド

### なぜ入れたか

このリポジトリの重要な不変条件は、すでに `scripts/check.ts` に検査として入っている
（配信バッジの中に別リンクを入れない／`SeasonExplorer`が`useSearchParams`をimportしない／
titleが幅の予算に収まる／過去クール索引とスナップショットがズレていない、など）。
**ところが2026-08-05まで CI が1本も無く**、この検査を回すかどうかは作業者
（人でも Claude でも）の裁量だった。

⑦-10 のSSR空HTML問題が2週間気づかれなかったのは、まさに検証手順が裁量に
委ねられていたからである。検査を手順書やプロンプトではなく**PRのゲート**に置けば、
誰が・どのモデルが作業しても同じ不変条件が必ず効く。日次巡回（Routine）が毎日出すPRも
ここを通るので、巡回セッションが検証を省略しても壊れた変更はマージ前に止まる。

### 設計上の注意

- **Node 22 が必須**。`node scripts/check.ts` は拡張子`.ts`をそのまま実行しており、
  Node 22.18+ の型ストリッピング（既定で有効）に依存している。他のワークフローは
  Node 20 だが、20 では `.ts` を実行できず必ず落ちる。**このワークフローだけ 22 にしてある。**
- **シークレット不要・外向き通信に依存しない**。`check.ts`と`check-threads.js`は
  ネットワークに出ない。`npm run build` は Annict への取得を試みるが、`ANNICT_TOKEN`が
  無ければ各ページが catch して`initialData`なしで完走する（ローカルでトークン未設定のまま
  ビルド成功を実測確認済み）。よって **Annict 側の障害で CI が赤くなることはない**。
- 裏返しの制約として、**この CI はデータに依存する表示までは検証しない**（型・不変条件・
  ビルド成否まで）。SSRページの中身が期待どおりかは、⑦-10 のとおり
  `npx next start` して `curl` で数える手作業が引き続き要る。

## ⑮ シーズンページのHTML量の見張り（2026-08-06導入）

### なぜ見張るのか

2026-08-05に⑦-10（SSRが空だった問題）を直した結果、シーズンページのHTMLは
**作品数に比例して増える**形になった。修正の前後で実測すると:

| | raw | gzip | 作品リンク |
|---|---|---|---|
| 修正前 `/season/2024/summer` | 188,215 B | 33,545 B | 0個 |
| 修正後 `/season/2024/summer` | 694,859 B | 57,373 B | 158個 |

増えたぶんは「今まで出ていなかった本文」そのものなので**これは削るべき無駄ではない**。
配信はISR＋CDNキャッシュ（`s-maxage=600`）に載るので、増分はエッジからの転送量に
乗るだけで、オリジンの待ち時間には効かない。2026-08-06時点で問題になる水準ではない。

ただし作品数が増え続ければいつかは重くなる。その「いつか」を人の記憶に頼らないよう、
機械的に見張る。

### しきい値と根拠

- 1作品あたり **raw 約4.4KB / gzip 約363B**（上表の158作品から算出）。
- 目安は **gzip 100KB ＝ 約282作品**。超えたら見直し対象。
- 2026-08-06時点の最大は **2024年秋の224作品（gzip推定79.4KB）**。目安の約8割。

### どこで気づくか

1. `node scripts/check.ts` の末尾「シーズンページのHTML量」。
   `content/snapshots/`の全クールから最大の作品数を取り、目安を超えたら`⚠`を出す。
   **落とさない**（作品数はAnnict側の登録数で決まり、そのPRの是非とは無関係なので、
   無関係な変更をブロックしてはいけない）。CIのログにも毎回出る。
2. 日次巡回（Routine）が上の`⚠`を拾い、日報に載せて通知する。
3. 現在クールの件数は**ネットワーク無しでは分からない**ので`check.ts`では見られない。
   現在クールは巡回が`/api/season?year=&season=`の`count`で見る。

### 超えたらどうするか（検討の順に）

1. **一覧の初期表示件数を絞り、続きは「もっと見る」で出す。** ただし
   `<a href="/anime/..">`がHTMLから消えるとクロール導線が減るので、
   出さない作品ぶんのリンクだけは残す（`hidden`でもクロールはされる）か、
   ⑦-11 で入れたsitemapに任せる判断をする。
2. **カード1枚あたりのHTMLを削る。** 配信バッジのマークアップが1作品あたりの
   大半を占めるので、ここの冗長さを削るのが単価に一番効く。
3. **クール内をページ分割する。** ただしURLが増え、順位を分散させるので最後の手段。

## ⑯ 配信先ウィジェット・公開API（被リンク施策・2026-08-06導入）

### なぜ作ったか（＝何を賭けているか）

2026-07-26の実測は「平均掲載順位19.8位・検索クリック7件/28日」。同じ実測で
**2026-07-13に新設したSEOページ群（`/exclusive` `/service` `/rankings`）は表示ゼロ**と分かり、
「ページの種類を増やす」方向は頭打ちと判定済み。7月末のtitle/description改善も、
順位そのものを動かす手ではない。

残っているボトルネックは**被リンク・外部言及がほぼゼロ**であること。個人サイトが
予算も知名度も無しに被リンクを得る現実的な手段は「他人が貼りたくなるものを配る」しかない。

アニメ感想ブログは記事末に「この作品はここで見られます」を書きたい動機を元々持っていて、
いまは自分で調べて手で書いている。そこを貼り付けコード1つで埋められるようにした。
**大手VODアフィリエイトサイトは同じことをすると自分の広告収益を他人に渡すことになるので
構造的に真似できない＝個人サイトだから打てる手**、というのがこの施策の賭けどころ。

手元のスナップショットで確認した前提（この判断の根拠）:

| クール | 配信情報あり | dアニメ単独カバー | 1社独占の作品 |
|---|---|---|---|
| 2025冬 | 69/201 | 81% | 13 |
| 2025春 | 87/176 | 78% | 18 |
| 2025夏 | 91/172 | 82% | 13 |
| 2025秋 | 88/187 | 74% | 21 |

＝「どこで見られるか」の答えはほぼ全作品で同じ。**一覧そのものには差別化の余地が無い**ので、
一覧で競合と殴り合うのではなく、一覧を**配って**言及を取りに行く。

### 何を出しているか

| URL | 中身 |
|---|---|
| `/anime/{id}` の「ブログ・サイトに貼る」 | 貼り付けコードのコピー欄（`components/EmbedSnippet.tsx`） |
| `/embed/anime/{id}` | iframe版ウィジェットのHTML（`app/embed/anime/[id]/route.ts`） |
| `/api/work/{id}` | 作品1件の配信情報JSON（公開API・CORS許可） |
| `/api/season` `/api/search-index` | 既存APIにCORSヘッダを追加して公開API化 |
| `/developers` | 貼り方・API仕様・利用条件の案内ページ |

貼り付けコードは2形式:
- **HTML** … 単一の`<a>`＋インラインstyleのみ。外部CSS/JSを読み込まないので貼り先の
  表示速度に影響しない。貼った時点の配信先で固定。
- **iframe** … `/embed/anime/{id}`を読む。配信先が変わると自動追従。貼り先のライト/ダークにも追従。

`/embed/anime/[id]`を**React のページではなく Route Handler**にしているのは、
`app/layout.tsx`（globals.css・Supabaseの`AuthProvider`・Vercel Analytics）を通さないため。
App Routerはルートレイアウトを外せないので、HTMLを直接返して回避している。
**他人のサイトの中で動くものに認証用JSと解析を持ち込まない**という判断でもある。

### 絶対に守ること（`node scripts/check.ts`が検査する）

埋め込みは**他人のサイトの中で表示される**ため、事故の影響が自サイトに閉じない。
「配信バッジの遷移先」（⑦-7）と同じ重大度で扱う。

1. **埋め込みHTMLに入るリンクは自サイト配下だけ。** アフィリエイトリンクを絶対に混ぜない
   （他人のブログに自分の広告リンクを埋めるのはステマ規制・ASP規約の両面で事故になり、
   貼る側の信頼も壊す）。`lib/embed.ts`が`lib/affiliate.ts`を参照しないことも検査している。
2. **`<script>`を含めない。** 他人のサイトで実行されるJSを配らない。
3. **作品名は必ずエスケープする。**
4. **リンクには`?ref=embed`を付ける**（流入の実測用。`docs/demand-scan.md`の`?ref=`と同じ運用）。

Googleは「ウィジェット経由のキーワード詰め込みリンク」をリンクスパムとして扱う。
そのためアンカーテキストは**作品名とサイト名だけ**にし、`/developers`にも
「リンクを外して使ってよい／見返りは提供しない（リンクの売買・交換はしない）」と明記している。
**キーワードを詰めたアンカーテキストに変えないこと。**

### 効果の見かた

- **コピーされた回数**: `/admin/analytics`の`embed_copy`イベント（`kind`＝`html`/`iframe`）。
- **貼られて流入したか**: Vercel Analyticsのリファラ、および`?ref=embed`付きURL。
- **被リンクとして効いたか**: Search Consoleの「リンク」→外部リンク元サイト。
  順位（19.8位）が動くとしたらここが先に動く。

コピー数だけ増えて流入が0のままなら「貼る動機はあるが読者に押されていない」＝文言・見た目の問題。
コピー数自体が0なら「貼る人がそもそも来ていない」＝告知の問題で、
`outreach-scout`で拾ったアニメ感想ブログへの案内（人力）が次の手になる。

### 貼ってもらう相手への案内（2026-08-06追加）

ウィジェットは**存在を知られなければゼロのまま**なので、⑯の効果は告知にかかっている。

- 候補リスト … `docs/outreach-candidates.md`の2026-08-06節
- 案内文テンプレート … `docs/outreach-widget-pitch.md`（**送信は人力**）

押さえておく点:

- **VOD比較アフィリエイトサイトには送らない**。検索上位はこの層だが、貼ると自分のアフィ収益を
  他人に渡すことになるので構造的に貼れない。**競合であって配布先ではない**（⑯の前提そのもの）。
  狙うのは「感想が主目的で、配信先は読者への親切として書いている」個人ブログ。
- **被リンクを依頼しない**。Googleのリンクスパム対策は「ウィジェット経由でリンクを配る」形を
  問題視しており、`/developers`にも「リンクを外して使ってよい」「リンクの売買・交換は行わない」と
  書いてある。案内は「使えるものを作ったのでよかったらどうぞ」で止める。
- **noteとアメブロにはウィジェットを貼れない**（noteは記事内に任意のHTMLを置けない、アメブロは
  iframeが禁止タグ）。毎クール全作品レビューを書いているのはnote層に多く、動機は最も強いのに
  渡せない、というねじれがある。この層にはサイト紹介のみに切り替える。
- 1回3〜5件まで。送った先は日付つきで`docs/outreach-candidates.md`に追記して二重送信を防ぐ。

## ⑰ 放送終了作品に「いま配信中」と書かない（2026-08-06修正）

### 何が起きていたか

2026-08-05に**過去クール64件・作品1,961ページを検索エンジンへ開放した**。ところが作品ページは
放送中か終了済みかに関係なく、全作品に対してこう書いていた:

> 「作品名」は dアニメストア・U-NEXT で視聴できます（2026-08-06時点）

**Annictのprogramsは「放送/配信の番組表の記録」であって、配信の現在の可否ではない。**
放送終了作品でも当時の配信枠がデータに残るだけで、Annictは「配信が終了した」ことを
記録しない（コミュニティ更新ベースのため）。つまり2015年冬の作品ページに出ていた
「2026-08-06時点で視聴できます」は、**誰も確認していない主張**だった。

CLAUDE.mdの「配信情報なしは仕様であり、勝手に推測データで埋めない」と同じ性質の問題で、
こちらは「無いものを書く」ではなく「**確認していないことを確認済みのように書く**」型。
開放直後＝索引に載り始めた直後だったので、傷が浅いうちに直した。

### どう直したか

判定と文面を`lib/workAvailability.ts`（純粋関数・`scripts/check.ts`から検査可能）に集約した。

- `airingStatus(基準日, 今日)` … 基準日（放送開始日、劇場作品は人力補完の公開日）のクールが
  現在クールより前なら`"finished"`。基準日が無い作品（放送日未定の新作）は`"airing"`
  （判定できないものを「終了」側へ倒すと、これから始まる作品にまで但し書きが出るため）。
- `"finished"`では現在形の断定をやめる。ただし**逆方向（「もう配信されていません」）も
  同じく未確認なので書かない**。事実である「配信情報がある」だけを述べ、確認を促す。

| 箇所 | airing（従来どおり） | finished |
|---|---|---|
| 可視テキスト・FAQ（JSON-LD） | 「〜で視聴できます（{日}時点）」 | 「〜の配信情報があるのは 〜 です（{日}時点のAnnictデータ）。放送が終了した作品は配信も終了していることがあるため、視聴前に各サービスの最新情報をご確認ください。」 |
| description（検索スニペット） | 「〜を見放題で配信している動画配信サービスは 〜」 | 「〜の配信情報があるのは 〜。放送終了作品のため、視聴前に各サービスで最新の配信状況をご確認ください。」 |
| Work JSON-LD の description | 「〜 で配信中。」 | 「〜の配信情報（〜）。{日}時点のAnnictデータ。」 |
| ウィジェットの見出しラベル | 「配信中のサービス」 | 「配信情報」 |

あわせて全作品共通で直したもの:

- **「配信情報の確認日」→「配信情報の取得日」**。「確認日」だと「その日に配信されていることを
  確認した」と読めるが、実際はAnnictからデータを取得した日でしかない。放送中の作品でも
  同じ誤解を招くので全作品で変えた。
- **公開API`/api/work/{id}`に`airingStatus`を追加**。二次利用する側が同じ誤りを繰り返さずに
  済むよう判定結果をそのまま公開し、`/developers`にも「`finished`を『配信中』と書くと
  未確認の主張になる」と明記した。

### なぜウィジェットまで直したか

埋め込みウィジェットは**他人のブログの過去作の感想記事**に貼られる可能性が高い。そこで
「配信中のサービス」と言い切ると、間違ったときに**貼ってくれた人の記事の信頼まで
巻き添えにする**。⑯の施策は「貼ってもらう」ことが前提なので、貼る側にリスクを渡す作りは
施策そのものを壊す。

### 再発防止

`node scripts/check.ts` の「放送終了作品の表現」節が固定している:

- クール判定（同クール／直前クール／前年／11年前／来年／基準日なし／クール境界）
- 放送終了の文面に「視聴できます」「配信中」等の**現在形の断定**が出ないこと
- 放送終了の文面が**終了も断定しない**こと（「視聴できません」等）、かつ確認を促す文があること
- 過去作のウィジェットHTMLに「配信中」が出ないこと
- 作品ページが`workAvailability`を経由すること（page.tsx側に文面のコピーが増えるのを防ぐ）

**この検査を消さないこと。** 文面を変えるときは`lib/workAvailability.ts`を直す（page.tsxや
embed.tsに直書きしない）。

### 本番での確認（2026-08-07に自動化した）

導入時（2026-08-06）は作品ページの本番HTMLを確認できずに終わった。Annictへの外向き
通信が遮断され（`.env.local`も無い）作品ページを描画できず、本番ドメインへの通信も
egress proxy にブロックされていたためで、これは**セッションを動かす環境しだいで
「やろうとしてもできない」**。実際この確認は3セッション連続で持ち越された。

そのため⑱の**本番SSRの実地検査**（`scripts/verify-production.sh` / 毎日実行）に
組み込んだ。過去クール作品ページに「配信情報があるのは」が入り「視聴できます」が
入っていないこと、放送中の作品には従来どおり断定形が出ていること、公開APIの
`airingStatus`が期待どおりであることを毎日検査する。**手で確認しなくてよくなった。**
`/developers`は導入時に確認済み（h1が1個・h2が5個・28KB・`airingStatus`の説明あり）。

### なぜ要るか

`node scripts/check.ts`（CI）は**ソースコードしか見ない**。ところがこのリポジトリで

つまり「ソース検査」と「目視」の両方をすり抜ける壊れ方が実在する。

⑦-10の再発防止として「本番HTMLを取って数える」手順は書かれたが、**実行は裁量のまま**
だった。結果、2026-08-06〜08-07の3セッション連続で持ち越され一度も実行されていない。
しかもセッション環境によっては本番ドメインへの外向き通信が遮断されている（2026-08-07実測:
egress proxy が `animedia-khaki.vercel.app` をブロック）。
**手順書に書くだけでは実行されない**ので、本番へ到達できる GitHub Actions に移した。

### 中身

`.github/workflows/verify-production.yml`（毎日1回＋手動実行）が
`scripts/verify-production.sh` を回す。条件はYAMLではなくシェルスクリプト側にあり、
外向き通信のある環境なら手元でもそのまま実行できる。

```
bash scripts/verify-production.sh
```

| 検査 | 何を守るか | 経緯 |
|---|---|---|
| A | シーズンページのHTMLに `<h1>` と作品リンクが入っている | ⑦-10 |
| A2 | 作品ページのHTMLに `<h1>` が入っている | ⑦-10 |
| B | 放送終了作品に「視聴できます」と書いていない | ⑰ |
| C | 放送中作品には従来どおり断定形が出ている | B の対 |
| D | 埋め込みに `<script>`・自サイト外リンクが無い | ⑯ |
| E | 公開APIが `airingStatus` とCORSヘッダを返す | ⑰ |

シークレット不要・公開URLの読み取りのみ。失敗は GitHub Issue（ラベル `production-check`）に
出す（scheduleの失敗メールは埋もれるため）。

### 設計上の注意

- **Cは消さないこと。** B（「視聴できます」が**無い**こと）だけだと、文言が変わって
  サイト全体からその文字列が消えたときに**黙って素通り**し、検査が無力化する。
  C（放送中の作品には出ている）と対にして初めて意味を持つ。
  さらに `node scripts/check.ts` が、`verify-production.sh` が探す文言と
  `lib/workAvailability.ts` の出力が一致することをPR時点で検査している。
- **検査対象の作品IDをハードコードしない。** 作品がAnnictから消えると検査自体が
  壊れるため、過去クールは `content/archive/index.json` のいちばん新しいクールから、
  現在クールは `/api/season` の注目度上位から選ぶ。検査文言は配信サービスが1件以上
  ある作品にしか出ないので、候補を `/api/work` で見て `services` が空でない最初の1件を使う。
- 本番が落ちていればこの検査も落ちるが、それは検知したい事象そのものなので問題ない。
- **検査スクリプト自身の検査**が `scripts/check-verify-production.js`（CIで毎PR実行）。
  シェルは静的検査が効かず、しかもこの種のスクリプトは「NGを出さなくなる」方向＝
  毎日緑のまま無力化する形で壊れるので、緑を見ていても気づけない。スタブの本番サーバーを
  立てて `verify-production.sh` を実際に子プロセス実行し、10種類の事故を1つずつ仕込んで
  **その事故だけを漏れなくNGにする**ことを固定してある（`scripts/check-threads.js` と同じ流儀）。
  `verify-production.sh` に検査を足したら、こちらのOK期待件数も更新する。

### セッションから検査したいときは、ローカルの本番ビルドで代用する（2026-08-10追記）

上の仕組みは毎日GitHub Actions側で回るが、**セッション中にその場で確かめたい**ことがある
（変更を入れた直後など）。外向き通信は遮断されていて本番URLは叩けないが、
**`localhost` はプロキシの `noProxy` に入っている**ので、ローカルで本番ビルドを起動すれば
同じ検査ができる。ネットワークもトークンも要らない（過去クールは
`content/snapshots/` から返るため）。

```bash
npm run build
npx next start -p 3100 &          # localhost は遮断されない
curl -sS http://127.0.0.1:3100/season/2024/autumn | grep -c '<h1'
curl -sS http://127.0.0.1:3100/season/2024/autumn | grep -o 'href="/anime/[0-9]*"' | sort -u | wc -l
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3100/anime/11771
```

**現在クールは使えない**（`ANNICT_TOKEN` とAnnictへの通信が要る）。
`content/archive/index.json` にある過去クールを使うこと。

2026-08-10に `/season/2024/autumn`（224作品）で実行した結果:

| 見るもの | 結果 |
|---|---|
| `<h1>` の数 | 1 |
| `/anime/{id}` への実リンク | 224（重複なし） |
| `/service/{key}/2024/autumn` への実リンク | 12（⑱-8の孤立ページ修正が効いている） |
| JSON-LD ブロック | 4 |
| 作品ページ `/anime/11771` | 200・`<h1>`あり・canonical正・FAQPageあり |
| 放送終了作品の文言 | 「配信情報がある」止まり。「視聴できます」は出ていない（⑰のとおり） |

**リダイレクトの検査**（GSCの「ページにリダイレクトがあります」を追うとき）:

```bash
for p in / /season/2024/autumn /anime/11771 /feed.xml /sitemap.xml /developers; do
  curl -sS -o /dev/null -w "$p %{http_code}\n" "http://127.0.0.1:3100$p"; done
```

2026-08-10時点で **3xx を返すのは末尾スラッシュ付きURLだけ**（`/about/` → 308 → `/about`）で、
これは Next.js の既定の正規化。sitemap にも内部リンクにも末尾スラッシュ付きURLは**1本も無い**
ことを確認済み（`grep -o 'href="/[^"]*/"'` が0件）。つまり**サイト側に意図しない
リダイレクトは無い**。GSCが挙げているURLの実体は、GSCの「ページのインデックス登録」
レポートを開かないと分からない。

## ⑱ カレンダー購読・出典表記・サービス別独占（2026-08-07導入）

世界の類似サービス約100件の調査（`docs/growth-strategy-2026-08.md`、生データは
`docs/research-2026-08/`）を受けて実装した3点。いずれも既存の資産を配り方の側で
使い切るもので、新しいデータ源は増やしていない。

### 1. `/calendar.ics`（カレンダー購読）

今期の放送・配信スケジュールを iCalendar で配信する。

| URL | 中身 |
|---|---|
| `/calendar.ics` | 今期の全作品（放送開始日が判明しているもの） |
| `/calendar.ics?service=d_anime` | そのサービスの**見放題**で見られる作品だけ |

**なぜ作ったか**: 調査で長生きしている側（しょぼいカレンダー・Annict・AnimeSchedule・
Senpai.moe・映画.com）は例外なく購読できるフィードを持っていた。MyAnimeList・AniList・
LiveChart・Simkl の流入はいずれも Direct が49〜77%で、検索ではなく**定着**で回っている。
`.ics` は一度購読されたらこちらが何もしなくても毎週相手のカレンダーに出る点で、
毎日投稿を出し続けるSNS運用とは性質がまるで違う。

**放送開始1週間前ルールとの関係**（CLAUDE.mdの基本ルール）:
UIで曜日・時刻を出さないのは「今週の水曜22:30」と誤読させないためで、
カレンダーは実日付を持つのでその誤読は起きない。ただし **DTSTART は必ず
`broadcastStartDate`（実際の放送開始日）に置く**。「次の水曜」から始めると
1話も配信されていない日に予定が入り、同じ誤誘導になる。
**放送開始日または時刻が分からない作品はカレンダーに載せない**（推測で日付を作らない）。

**実装上の注意**:
- ロジックは `lib/calendar.ts`（素の`.ts`なのは`node scripts/check.ts`から検査するため）
- Annict障害時は**空のカレンダーではなく503を返す**。空を返すと購読者の予定表が
  丸ごと消える（購読クライアントは503なら前回の内容を保持する）
- 「26:30」のような24時以降の放送業界表記は翌日に繰り上げる
- 改行はCRLF・作品名はRFC 5545のエスケープ（カンマ・セミコロンを含む作品名で
  イベントが壊れる）。`node scripts/check.ts`の「カレンダー購読」節が8項目を検査する

### 2. 出典表記（`lib/attribution.ts`）

**なぜ**: 公開APIとウィジェットは2026-08-06に出したが、「出典を明記してください」が
利用条件の箇条書きにあるだけで**そのまま貼れる形が無かった**。調査で被リンクを継続的に
得ている側（駅データ.jp・TMDB・Open Food Facts）は、いずれも出典の書き方を
用意していた。使う側は書きたくないのではなく、自分で文面を組み立てる手間があると
省くだけなので、コピーできる1行を出す。

- `/developers` に「出典の書き方」節（HTML / Markdown / テキストの3形式）
- 公開API（`/api/work/{id}`・`/api/season`）の `source` を同じ形に統一。
  `attribution` フィールドに文面がそのまま入る
- 出典リンクからの流入は `?ref=credit` で実測する（ウィジェットの`embed`・
  カレンダーの`ics`と区別できる）

**方針**: これは**リンクを義務にして被リンクを買う施策ではない**。Googleはリンクの
売買・交換をリンクスパムとして扱う。`/developers` の「リンクを外して使ってよい・
見返りは提供しない」は据え置きで、**書きたい人が書けるようにする**だけ。

### 3. サービス別ページの「{サービス}でしか見られない作品」

`/service/[key]/[year]/[season]` の先頭に、そのサービスの**独占作品**（見放題が
ちょうど1社＝`/exclusive`と同じ基準）を出す。

**なぜ先頭か**: dアニメが各クールの74〜82%をカバーする以上、複数社で配信されている
作品は「どこで見ても同じ」であって加入の理由にならない。**利用者に「このサービスに
入るか」の判断が発生するのは独占作品の場面だけ**なので、アフィリエイトの転換率が
構造的に最も高い面になる。既存の`/exclusive`はクール軸だが、加入判断は
「ABEMAに入るべきか」というサービス軸で起きる。

### 4. 配信状況の集計（`scripts/streaming-trends.ts`）と、年次比較の禁止

`node scripts/streaming-trends.ts [--post]` で、スナップショットから
「各クールの注目度上位30作品」の配信状況を集計する。ネットワークには出ない。

**このデータで年次の推移を主張してはいけない**（2026-08-07に2回続けて読み違えた）。

1回目: 全作品で集計して「Netflixの掲載率が31〜42%→16〜32%に後退」と読んだ。
誤り。収録が良くなってNetflixに載らない小規模作品が母数に加わっただけで、
**分母が変わっていた**。上位30作品で見ると54%→47%のほぼ横ばい。

2回目: 上位30作品に絞れば補正できたと考え「独占12%→4%」「平均3.2→9.0社」
「ABEMA 21%→94%」を採用した。これも誤り。この絞り込みが補正するのは
**作品単位**の収録（配信情報が1件でもあるか）だけで、**サービス単位**の収録
（配信社が漏れなく記録されているか）は補正していない。
決め手は**U-NEXTの掲載率が2021年=0%→2023年=79%**と出ること。U-NEXTが2021年に
アニメを配信していなかったはずはなく、記録漏れである。
サービスが記録漏れすると作品は実際より「独占」に見え平均社数は少なく出るので、
**収録改善だけでも「独占が減った・マルチ配信化した」と同じ形になる**。

**外向けに使ってよいのは、記録が濃い直近年の断面だけ**（`currentState()`）。
断面なら記録漏れの向きの影響を受けない（漏れがあるなら実際はこれ以上、としか言えない）。
2025年の実績: 上位30×4クールで配信率100%、平均9.0社、1社独占4%、
dアニメ93% / ABEMA94% / Prime96% / U-NEXT89% / Netflix47%。

`node scripts/check.ts` の「配信集計の年次比較を禁じる」節が、
`lib/streamingTrends.ts` に年次差分を返す関数が生えていないことを検査する。

**一般則**: 割合の変化を見るときは ①分母の変化 と ②観測されるかどうかの変化
の両方を疑う。①は上位N絞り込みで潰せるが**②は潰せない**。②が疑わしいなら推移を出さない。

### 6. 声優ページに「他のクールの出演作」を追加（2026-08-07）

`/person/[name]/[year]/[season]` は名前のとおり**そのクールの出演作しか出せなかった**。
だが「この声優の出演作、どれがどこで見られるのか」はクールに閉じた問いではない
（調査は `docs/research-2026-08/research-I.md`。知恵袋等で繰り返し聞かれており、
答えているのは「同じ声優が演じたキャラ○選」型のまとめ記事で、**配信先まで一緒に
答えているものは見当たらなかった**）。

スナップショットが `castNames` を持っていたので、Annictへの追加取得ゼロで作れた。
`node scripts/build-person-index.ts` → `content/archive/people.json`（787人・出演7,721件）。

収録方針は `content/archive/index.json` と同じ:

- **配信情報が1件以上ある作品だけ**（配信0件の作品ページは「配信情報なし」としか
  答えられないので、そこへのリンクを声優ページから大量に生やさない）
- **出演2作品以上の人だけ**（1作品の人はクール別ページと中身が同じになる）
- 1ページの表示は新しい順に24件まで（多作な声優でページが縦に伸びきるのを防ぐ）

**表現の制約**: ここに並ぶのは「そのクールの番組表に配信の記録があった」作品であって、
いま配信されている保証は無い（⑰と同じ）。見出しは「配信情報がある作品」で、
「配信中」「視聴できます」とは書かない。

副次的な効果として、**過去クールの作品ページへの内部リンクが増える**。
2026-08-05にsitemapへ載せた過去作1,961ページは、それまでシーズンページからしか
辿れなかった。

`node scripts/check.ts` の「声優の出演作索引」節が、スナップショットとの一致・
配信0件の混入・出演1作品の混入・同一クールの二重表示を検査する。
**スナップショットを再生成したら `node scripts/build-person-index.ts` も回す**
（`build-archive-index.ts` と同じ扱い）。

### 7. 日次のX下書きIssueをワンタップで開けるようにした（2026-08-07）

2026-08-06に週次X成長キットへ入れた「タップ1回でXの投稿画面が本文入りで開くリンク」
（`scripts/lib/x-intent.js`）が、**毎日起票される日次の下書きIssueには入っていなかった**。
日次側は本文がベタ書きで置かれているだけで、スマホから投稿するには
「長押しで選択 → コピー → Xアプリに切替 → 貼り付け」が要る。
実測では日次の下書きIssueが7/31以降7件連続でopenのまま止まっていた。

### 8. サービス別ページが「孤立ページ」だったのを直した（2026-08-07）

`/service/[key]/[year]/[season]` は2026-08-06までに実装され、`app/sitemap.ts` にも
載せていた。しかし **サイト内からこのページへのリンクが1本も無かった**。
画面上部の配信サービス絞り込みチップは `<button>` でクライアント状態を変えるだけで
`<a href>` を持たないため、ブラウザで触っている限り「サービス別に見る導線はある」と
錯覚する。2026-08-05に他クールへのリンクで踏んだ穴と同型で、
**画面を見て気づくことができない種類の欠落**。

痛いのは、`docs/growth-strategy-2026-08.md` の Tier 3⑥ が
「dアニメが74〜82%をカバーする世界で、利用者に新規加入の判断が発生する唯一の場面は
独占作品であり、加入判断はサービス軸で起きる」と整理していたことで、
つまり **アフィリエイトの転換が起きうる唯一の面へ、人もクローラーも到達できない**
状態のまま、sitemapにだけURLが並んでいた。

直したのは3箇所:

- `components/SeasonExplorer.tsx` の「他のクールのアニメ配信情報」ナビに
  「配信サービス別:」の行を追加（そのクールで見られる本数の多い順）。
  トップ・シーズンページの両方がサーバーHTMLにこのリンクを含む。
- `app/anime/[id]/page.tsx` の関連作品ブロックの下に
  「{サービス}で見られる{年}年{季節}アニメ」へのリンク。
  **バッジ列の外**に置き、文言つきのテキストリンクにしてある
  （バッジの中に別行き先のリンクを入れない、記号だけのリンクにしない、の両ルール）。
- `app/service/.../page.tsx` に `/calendar.ics?service=` の購読導線
  （`components/CalendarSubscribeLink.tsx`）。**今期のページでだけ出す** ——
  `/calendar.ics` は year/season を受け取らず常に今期を返すため、過去クールの
  ページに置くと「2020年冬の予定表」を期待した人に今期のカレンダーを渡すことになる。

`node scripts/check.ts` の「孤立ページを作らない（内部リンク）」節が、
`SeasonExplorer` と作品ページの両方から `/service/` へのリンクが消えていないかを検査する。

### 9. 次クール準備の前倒しIssue（2026-08-07導入）

このサイトの検索需要はクール単位で、次クールの検索はクール開始の約1ヶ月前から
立ち上がる。**山は年に4回しか来ないので、始める時期を外すと次は3ヶ月後**になる。
にもかかわらず「前倒しで準備を始める」きっかけが運用のどこにも無かった
（`season-announce.yml` はクール開始当日の告知で、準備の号令ではない）。

`.github/workflows/season-prep.yml` が毎日1回起動し、
`scripts/lib/build-season-prep.js` が「いまが窓の中か」を判定する。窓は
**8月下旬→秋 / 11月下旬→翌年の冬 / 2月下旬→春 / 5月下旬→夏**（いずれも21日〜月末）。

- cronは「毎日1回」の意味しか持たせず、**月日をYAMLに書かない**
  （scheduleが数時間遅れても窓の中のどこかで必ず当たる。`SLOTS`と同じ方針）。
  `check.ts` がcronの月・日フィールドが `*` であることと、4つの窓が意図した
  対象クールを返すこと（特に11月下旬が**翌年**の冬になること）を検査する。
- 窓は10日前後あり毎日「窓の中」を返すので、Issueタイトルにクール名を入れ、
  `gh issue list --state all` の同名検索で二重起票を防ぐ。closedも見るのは、
  対応が終わって閉じた後の日に再起票しないため。

Issueの中身は `audit-coverage.ts` の点検 →`extraServices.ts` の人力補完 →
`spotlight.js` の入れ替え → 年またぎ時のスナップショット再生成 → 次クールページの
インデックス確認。`audit-coverage.ts` は `ANNICT_TOKEN` が要るのでローカルPCで回す。

**この窓（8月下旬など）でできるのは作品リストの把握までで、配信先の網羅は終わらない。**
配信ラインナップの発表は業界全体で9月中旬〜10月上旬に集中するため（2026-08-12調査）、
配信の穴埋めはその時期にもう一度手を入れる必要がある。Annict単独の到達点・
人力で埋めるべき残りの規模・配信サービス側のラインナップページから当たる手順は
`docs/next-season-coverage.md` にまとめてある。

### 11. 制作会社・監督の横断索引（2026-08-07・土台のみ。データは再生成待ち）

声優でやった横断（⑱-6）を制作会社・監督にも広げようとして、**現状のスナップショットでは
作れない**ことが分かった。`creditNames` は役割を落としたフラットな配列で、
声優・制作会社・原作者・監督が混ざっている:

索引側は `lib/studioIndex.ts` ＋ `scripts/build-studio-index.ts` →

**配信情報が1件以上ある作品だけ・2作品以上ある会社/監督だけ**。

### 12. 視聴プラン（お気に入りを全部見るのに必要な最小のサービス組み合わせ・2026-08-07導入）

このサイトは「その作品がどこで見られるか」には答えていたが、利用者が実際に迫られる判断は
**「結局どれに入ればいいのか」**という組み合わせのほうだった。dアニメストアが74〜82%を
カバーする世界では作品単位の答えはほぼ同じになり、差がつくのは「自分が見る5〜10本」を
まとめて見たときだけ。ここは実データが無いと計算できないので、静的な「おすすめVOD比較」
記事では原理的に埋められない。

さらに、VOD比較アフィリエイトサイトは収益が契約数に比例するため
**「最小の組み合わせ」を教える動機を持たない**。利用者の利益と自サイトの収益が一致する側に
立てる、数少ない機能になる。

- 入力は**お気に入り**（`localStorage`・ログイン不要）。ログインを要求しない。
- レンタル/都度課金は「契約すれば見られる」ではないので数えない（対応本数の集計と同じ扱い）。
- 配信情報が無い作品は組み合わせに含めず、別枠で「未登録」と明示する（推測で埋めない）。
- 過去クールの作品について「いま配信されている」とは書かない（`lib/workAvailability.ts` と同じ）。

#### 表示速度の約束（利用者の指定: 一覧表示が2秒以上かからないこと）

1. **カード1枚ごとにマークアップを足さない。** シーズンページのHTMLは作品数に比例するので、
   カード内に何かを足すと最大クールで一気に効く（⑮の見張り対象）。追加は折りたたみ1つだけ。
2. **計算は開いたときだけ走らせる。** `planOpen` を `useMemo` の依存に入れて門番にしてある。
   一覧の描画・検索・絞り込みの経路では `buildServicePlan` は1度も呼ばれない。

実測（`npx next start` ＋ Chromium）:

| | 実測 |
|---|---|
| シーズンページのHTML | 696,771バイト → **696,771バイト**（変化なし） |
| 一覧が出るまで | 547ms |
| パネルを開いて結果が出るまで | 152ms |
| 計算そのもの（最大クール224作品） | 0.5ms |

`node scripts/check.ts` の「視聴プランの計算」節が、正しさ（貪欲法では1社多くなる形で
厳密解を返すか）と速さ（実データで200ms以内）の両方を見張る。

#### 表示上の注意（誤読の防止）

候補が複数あるとき、並んだサービス名を「全部に入る必要がある」と読まれると**逆の意味**になる。
候補どうしは「いずれか1つ」なので、見出しで明示し各行に「案1/案2」を付けてある。
1つの案の中のサービスは全部必要なので、そちらも括弧書きで補っている。

#### 料金を出さない理由（2026-08-07・利用者の判断）

月額料金を出すと「一次情報＋確認日」で価格改定を追い続ける運用が1つ増える。
いまは本数と組み合わせだけにして、様子を見る。

### 13. 「配信サービスが追加された」の検知を、メール通知に繋がない（2026-08-07・方針）

`/api/notify` の配信開始メールは既に動いている（毎日 `/api/notify/run` を叩く）。ここへ
「Annictに新しい配信サービスが登録された」を流す案は**採用しない**。

理由: 既存の通知は「その日に放送がある」という**日付駆動**なので1日1通に収まるが、
サービス追加は**変更駆動**で、上流の編集回数がそのまま通知回数になる。Annictは
コミュニティ編集なので、登録ミスの取り消しや付け直しがそのまま「イベント」に見え、
**利用者に上流の揺れが届く**。

将来サイト内表示だけでも出す場合は、最低限これを入れること:

- **消えたことは扱わない**（編集ミスの可能性が高く、そもそも「もう配信されていません」とは書かない方針）
- **連続N日見えてから確定扱い**にする（付けて消してを繰り返す編集はここで落ちる）
- **一度出した (作品×サービス) は永久に再掲しない**（消えて付け直されても2回目は出ない）
- **放送中のクールだけ**（過去作の遡り登録が一気に流れ込むのを防ぐ）

### 14. Discordスラッシュコマンド（2026-08-07導入・**Discord側の設定待ち**）

`docs/growth-strategy-2026-08.md` の Tier 2④ が「ホスティング費用の判断待ち」で
止まっていたが、**判断そのものが不要だった**。Discordには常時接続する Gateway 方式の
ほかに **Interactions Endpoint**（ただのHTTPエンドポイント）方式があり、
後者なら既存のVercelに相乗りできる。新しい費用も運用先も発生しない。

実装・検証済みのもの:

- `lib/discord.ts` … Ed25519の署名検証と返信文面（素の`.ts`。`check.ts`から検査）
- `app/api/discord/route.ts` … 受け口（`runtime = "nodejs"`。`node:crypto`を使うため）
- `scripts/check.ts` の「Discordスラッシュコマンド」節 … 署名検証5件＋文面4件

実際に鍵を生成して `npx next start` に投げ、通しで確認した:

| リクエスト | 結果 |
|---|---|
| PING（正しい署名） | 200 `{"type":1}` |
| PING（壊れた署名） | **401**（Discordが登録時に確かめる挙動） |
| `/anime title:リゼロ` | 200 type 4 のメッセージ |
| 作品名なし | 200 使い方の案内 |

**残りはDiscord側の設定だけ**（アプリ作成 → `DISCORD_PUBLIC_KEY` を環境変数に →
Interactions Endpoint URL 登録 → コマンド登録 → サーバーに追加）。手順は
`docs/discord-setup.md`。環境変数が未設定の間は503を返すだけで、サイトの他の機能に影響しない。

#### 設計上の制約（変更するときに壊しやすい点）

- **署名検証は生のリクエストボディで行う。** `JSON.parse` して `stringify` し直すと
  キー順や空白が変わって検証に失敗する。
- **遅延応答（type 5）は使わない。** サーバーレスで「返した後に続きを実行する」形は
  壊れやすい。今期のキャッシュ済みデータ（15分・`warm-cache.yml`で温め済み）で即答し、
  2秒で間に合わなければサイトへのリンクを返す。そのため**過去クールの横断検索はしない**。
- **放送終了作品にサービス名を並べない。** 返信は他人のサーバーに残るので、
  誤りの影響が自サイトに閉じない（⑰と同じ制約を、より強く適用する）。

### 15. 配信サービス追加の検知（2026-08-07導入・**Supabaseのテーブル作成待ち**）

⑱-13で決めた方針（メール通知には繋がない）を守ったうえで、検知そのものを実装した。
セットアップは `docs/service-additions-setup.md`、判定は `lib/serviceAdditions.ts`。

| | |
|---|---|
| バッチ | `POST /api/service-additions/run`（`x-cron-secret`。既存の `NOTIFY_CRON_SECRET` を流用） |
| 読み出し | `GET /api/service-additions`（直近14日・最大50件・CORS許可） |
| 自動実行 | `.github/workflows/service-additions.yml`（毎日1回） |
| 保存先 | Supabase `service_sightings`（**SQLを1回流す作業が要る**） |

残っているのはテーブル作成だけ。未設定の間は `{"skipped":true}` を返すだけで、
他の機能に影響しない。**確定が出始めるのは最短で導入の3日後**（連続3日ルール）。

#### 揺れを利用者に届けないための4つの保証

`scripts/check.ts` の「配信サービス追加の検知」節が全部テストしている。

1. **消えたことは扱わない**（行も消さず報告もしない。Annictは配信終了を記録しない）
2. **連続3日見えてから確定**（1日でも途切れたらやり直し＝付けて消してを繰り返す編集は落ちる）
3. **一度報告した組は永久に再報告しない**（消えて付け直されても2回目は出ない）
4. **初回は種まき**（既存の全ペアを黙って報告済みにする。これが無いと初日に全件が「新規」に見える）

加えて、同じ日に2回叩かれても二重に進まない（scheduleの遅延・再実行に強い）。
上流が落ちている日は「全サービスが消えた」ように見えるが、その日は**何も書かずに終わる**
（連続日数を壊さないため）。

#### 表示側にはまだ繋いでいない

`GET` は用意したが、日次SNS投稿にもサイトにも繋いでいない。どのみち3日は空なので、
データが溜まってから判断する。繋ぐときの文面は「◯◯で配信開始」と断定せず
**「配信情報に◯◯が追加されました」**にすること（Annictへの登録＝配信開始とは限らない）。

## ⑳ 声優データの取りこぼし（2026-08-11修正・重大度高）

### 症状

利用者からの指摘:

> 作品ページにて、声優のリンクが付いていないページがあります（悠木碧：リンクついていない）。
> 検索でも悠木碧が1作品しかヒットしない。

### 原因

`lib/annict.ts` のシーズン一覧クエリが `casts(first: 5)` しか取っていなかった
（`CASTS_LIST = 5`）。「一覧＝検索用だから主要5件で足りる」という前提が誤りで、
実際は次の**全部**がこの5件だけを見ていた。

| 依存している機能 | 実装 |
|---|---|
| 検索欄の声優名マッチ | `components/SeasonExplorer.tsx` |
| 声優ページの出演作一覧 | `app/person/.../page.tsx` の `findWorks` |
| 作品ページの声優リンクを出すか否か | `app/anime/[id]/page.tsx` の `linkableCastNames` |
| sitemapに載せる声優ページの選定 | `app/sitemap.ts` |
| 過去クールの声優索引 | `content/archive/people.json` |

実データでの切断率は **2025夏の172作品中87作品（50.6%）がちょうど5件**。
6件以上の作品は1つも存在しなかった（＝上限で切られている証拠）。

つまり6番目以降にクレジットされた声優は「そのクールに出演していない」のと同じ扱いになる。
さらに**「そのクールに2作品以上」という閾値（`PERSON_PAGE_MIN_APPEARANCES`）と噛み合う**ため、

- 5番目以内に入った作品が1つしか無い声優 → **リンクが消える・声優ページごと消える**
- 検索しても1作品しか出てこない

という形で壊れる。**例外もエラーも出ない**ので、画面を見ている限り気づけない。

### 直し方

`CASTS_LIST` を 40（＝作品ページ用の `CASTS_DETAIL` と同じ）に上げた。
転送量の心配は実測で否定できる。**castNamesはJSON全体119KBのうち3KB（3.3%）**しかない。
あわせて、一覧クエリからは `character { name }` を落とした（キャラクター名を使うのは
作品個別ページだけなので、増分の一部を相殺できる）。

`node scripts/check.ts` の「声優データの取りこぼし」節が下限（20件）を見張る。

### 【要対応】過去クール分はスナップショットの再生成が必要

`content/snapshots/` は**旧設定（5件）で生成されている**ため、過去クールは直っていない。
`content/archive/people.json`（787人）も、それを元に作られているので同じく過少。
現状の切断率は `node scripts/check.ts` が毎回表示する（**全4,121作品中3,622作品=87.9%が
ちょうど5件**。※声優データが1件でもある作品のうちの割合）。

再生成の完全な手順は **`docs/snapshot-regenerate.md`** にある。要点だけ再掲:

```bash
git switch main && git pull origin main     # ← 先に修正を取り込む（これを忘れると無意味）
node scripts/snapshot-past-seasons.ts 2010 2025 --force
node scripts/build-archive-index.ts
node scripts/build-person-index.ts
node scripts/build-studio-index.ts
node scripts/check.ts                       # 切断率が下がっていること
```

**注意**: `--force` の途中で `✗` が出た年は、**そのまま再実行しても直らない**
（古いファイルが残っているため `--force` 無しだとスキップされる）。
失敗した年を指定して `--force` で取り直すこと（例: `node scripts/snapshot-past-seasons.ts 2017 2017 --force`）。

再生成後は `people.json` の人数・出演件数が増え、sitemapに載る声優ページも増える。
`roleCredits` も入るので `content/archive/studios.json`（いまは空）も埋まる。

### なぜAnnictの`seriesList`を使わないか

Annictにはシリーズを表す `seriesList` がある。だが**この作業環境にはトークンもAnnictへの
通信も無く、実際の応答を確かめられない**。未検証のフィールドをシーズン一覧のGraphQLに足すと、
フィールド名や形が違ったときにクエリ全体がエラーになり、**全作品の配信情報が消える**。
得られるのは内部リンク、失うのはサイトの根幹で、交換として釣り合わない。

`content/works/extraServices.ts`・`releaseDates.ts` と同じ**人力補完**の方式にした
（`content/works/series.ts`）。トークンのある環境で `seriesList` の応答を確認できたら、
そのとき自動化を検討する。

### 方針

- 一次情報で確認できたものだけ。`sourceUrl` と `confirmedDate` は必須
- **作品名から「◯期」を機械的に推測して繋がない**。同名の別作品・スピンオフ・総集編を
  誤って繋ぐと、利用者を無関係なページへ送る
- 全作品は追わない。**GSCで需要が確認できた作品から都度追加**する
  （`content/works/*.json` の `faq` と同じ考え方）
- 放送が終わったシリーズ作品に「いま配信中」と書かない（基本ルール）。
  この欄は作品ページへのリンクとシリーズ内の位置（第1期など）を出すだけで、
  配信の現在の可否には触れない

### 検査

`node scripts/check.ts` の「シリーズの対応表」節が4点を見張る。

1. 出典と確認日がある
2. 1シリーズに2件以上ある
3. 同じ作品IDが複数のシリーズに出てこない
4. 作品ページが実際に `seriesFor` を使って描画している

スナップショットに存在するIDは実在する作品名との照合結果も表示する
（`10591=逃げ上手の若君`）。

### 確認済み

本番ビルドを起動して `/anime/10591` のHTMLを実取得し、次を確認した。

- 「「逃げ上手の若君」シリーズの他の作品」の見出しが出る
- `<a href="/anime/14132">逃げ上手の若君（第2期）</a>` のリンクが出る
- 出典（公式サイト）へのリンクと確認日が出る

第2期のページ（今期）はAnnictへのライブ取得が要るため、トークンの無い環境では
本文を描画できず未確認。描画経路は同一で、`seriesFor` が両方のIDから同じシリーズを
返すことは `check.ts` が検査している。

## ㉔ 面ごとの推移を測れるようにした（GSC取得の拡張・声優ページのISR化）2026-08-11

### なぜやったか

㉓で「声優ページ5.8位・CTR9.5% / 作品ページ22.3位・1.3%」という差が出たが、
これが**面の実力なのか季節性なのか区別できなかった**。
「作品名＋配信」は放送中しか需要が立たないのに対し、「声優名」は放送に紐付かない。
夏クール中盤という観測時期を考えると、差の一部は季節性かもしれない。

区別できなかった理由ははっきりしていて、`scripts/fetch-gsc.js` が
`date` / `query` / `page` を**別々の軸**で取っており、**面ごとの時系列というデータが
どこにも存在しなかった**から。日別の合計とページ別の合計はあるが、
「その日、作品ページは何回表示されたか」が無い。

### やったこと1: `weeklyByType` の追加

GSCは**16ヶ月ぶん保持**しているので、待つ必要はない。`date`×`page` の交差表を
長期（既定480日 = `GSC_LONG_WINDOW_DAYS`）でまとめて取れば、過去分も含めてその場で答えが出る。

ただし生の `date`×`page` 行をそのままコミットすると、日々のスナップショットが肥大化する。
そこで**取得直後に「週 × 面」へ畳んでから**書き出す。

- 分類と集計: `scripts/lib/gsc-page-type.js`（`pageType` / `weekStart` / `aggregateWeeklyByType`）。
  **面の分類はこのファイルだけが持つ。**集計する側と読む側で分類がズレると、
  数字が合わない原因を後から追えなくなる
- 面は トップ / 作品 / 声優 / サービス別 / シーズン / 独占 / ランキング / その他 の8種
- 粒度が「週」なのは、日次だと細かすぎ月次だとクール（3ヶ月）の中の推移が見えないため
- `ctr` / `position` は**表示回数で重み付け**する（既存の `summarize` と同じ理由）
- **表示もクリックも0の組は書き出さない**。サイトが小さいうちはほとんどの週×面が0で、
  そのまま書くとファイルが無意味に膨らむ
- 25,000行を超える場合は `startRow` でページ送りする。50,000行で打ち切るが、
  **打ち切ったときは黙らずログに出す**（「全部取れた」と誤読すると分析が静かに歪む）

出力は `content/analytics/gsc/<日付>.json` の `weeklyByType`（`longRange` に取得期間）。

### やったこと2: `process.exit(1)` → `process.exitCode = 1`

`check-gsc.js` を実行したら、**変更前から**「一部失敗: 終了コードは1」が落ちていた
（終了コード `3221226505` = `0xC0000409`）。Windowsで標準出力がパイプのとき、
書き込みが残ったまま `process.exit()` するとプロセスが異常終了する。
ログを何行も出したあとの経路なので必ず踏む。

`ci.yml` は ubuntu で回るので**CIは緑のまま**で、
**Windowsのローカルでだけ常に赤い**＝「CLAUDE.mdが必ず実行しろと言っている検査が、
手元では常にNGを出すので誰も信用しなくなる」形で放置されていた。
`process.exitCode` にすればNodeが出力を吐き切ってから終了するので値がそのまま伝わる。

### やったこと3: 声優ページのISR化

`app/person/[name]/[year]/[season]/page.tsx` に `revalidate = 900` と
`generateStaticParams`（空配列）を追加した。

**sitemapに載っている面のうち、声優ページだけが毎リクエスト動的描画だった**
（`/anime/[id]`=900秒、`/service/...`=600秒、`/season` `/exclusive` `/rankings` はISR済み）。
2026-07-13に作ったときも、2026-08-07に過去クール4,483ページへ広げたときも入れていなかった。
**実測で最も成績の良い面が、いちばん遅く返る面でもあった**ということ。

作品ページで測った同じ変更の効果は初回0.81秒 → 2回目以降0.010秒
（`app/anime/[id]/page.tsx` のコメント）。

**確認済み**: `npm run build` の出力で `/person/[name]/[year]/[season]` が `ƒ`（動的）から
`●`（SSG）に変わり、`.next/prerender-manifest.json` の `dynamicRoutes` に載ることを実測した。

**このページに `loading.tsx` を置かないこと。** 出演2作品未満で `notFound()` を返すため、
ストリーミングでヘッダが先に確定すると404が200（ソフト404）になる（作品ページで実測済み）。

### 保留にしたこと: 季節を含まない声優ページ `/person/[name]`

声優ページのURLは `/person/[名前]/[年]/[季節]` で**季節に紐付いている**。
声優の人気が通年なら、季節を含まないクエリの受け皿が無いのが弱点になりうる。

**が、いま作らない。** 理由:

1. **需要が確認できていない。** GSCで実際に取れているのは「悠木碧 2026」＝**年を含む**クエリで、
   季節を含まないクエリの受け皿が足りていないという証拠はまだ無い
2. 1,531人ぶんの新URLを作ることになり、既存4,483ページとの**内容の重複**が生じる。

### 追記: 手元で常に赤かった検査を2つ直した（2026-08-11・同じ調査の副産物）

`node scripts/check-gsc.js` を実行したときに、**変更前から**落ちている検査が他にも
あることが分かった。どちらも**CI（ubuntu）は緑・Windowsの開発機だけ常に赤**で、
「CLAUDE.mdが必ず実行しろと言っている検査が、手元では信用できない」状態だった。

| 検査 | 原因 | 直し方 |
|---|---|---|
| `check-probe-series.js`（3件NG） | `scripts/probe-series.ts` の `process.exit()` が13箇所。上と同じWindowsの異常終了（`3221226505`） | 全部 `process.exitCode` + `return` に置換 |
| `check-verify-production.js`（14件NG） | `scripts/verify-production.sh` が **`jq` に依存**していた。ubuntuランナーには同梱だがWindowsには無く、検査対象を1件も選べずに終了していた | `jq` を `scripts/lib/json-pick.js`（Node）に置き換え。**検査の中身は変えていない** |

`jq` の置き換えで、`verify-production.sh` の依存は curl と node だけになった。
Node はこのリポジトリの前提そのものなので、これで**どの環境でも同じように動く**
（CLAUDE.md・本書がどちらも「ローカルでも実行できる」と書いているのに、
実際には Windows で実行できていなかった）。`.github/workflows/verify-production.yml`
にも `setup-node` を足して、ランナー画像の暗黙の同梱に頼らないようにした。

**確認済み**: 置き換え後も `check-verify-production.js` は17項目すべてOKで、

埋め込みに`<script>`・CORSが消えた等）も全部NGを出す。検査は緩んでいない。

**教訓**: 「CIが緑」は「検査が働いている」と同義ではない。CIは1つのOSでしか回らないので、
**手元で全部の検査を通してから触る**。今回は3セッション以上にわたって
2つの検査が赤いまま放置されていた。

### 追記2: 「手元だけ赤い」が起きない構造にした（2026-08-11）

上の追記は「手元で全部の検査を通してから触る」という**手順**で終わっていた。しかし
このリポジトリで手順に委ねたものは実行されない（⑦-10の本番HTML確認が3セッション
連続で持ち越された件、`verify-production.sh` をGitHub Actionsに移した理由がそれ）。
同じ轍なので、機械に移した。

**やったこと**

1. **CIをubuntuとwindowsの両方で回す**（`.github/workflows/ci.yml` に matrix）。
   今回の2件はどちらもWindows固有で、**ubuntuだけで回している限り原理的に検知できない**。
   検査を増やしても環境が1つでは同じことが起きる。開発機と同じOSをCIに含めるのが
   唯一の構造的な対処になる。費用は、差が出にくく最も重い `npm run build` を
   Linux側だけにして抑えた（Windowsランナーはubuntuの2倍消費する）。
2. **`npm run check` を足した**。検査が6コマンドに分かれていると「全部通してから触る」は
   実際には守られない。1コマンドにまとめ、`node scripts/check.ts` が
   **CIの `run:` と `npm run check` が同じ検査を並べていること**を突き合わせる
   （片方に足してもう片方を忘れると落ちる）。
3. **`.gitattributes` で `*.sh` をLFに固定した**。この調査中に、`core.autocrlf=true` の
   影響で `verify-production.sh` が**CRLFで作業ツリーに展開されていた**ことが分かった。
   bashは行末のCRを引数の一部として読むため `set: pipefail: invalid option name` /
   `$'\r': command not found` となり、**スクリプトが1行も実行できない**。
   Git同梱のbashはCRを許容するので Git Bash からは気づけず、CIのubuntuはLFで展開する
   ので永久に緑。「特定のシェルからだけ必ず落ちる」という、まさに同じ形の穴だった。
4. **`check-verify-production.js` が使うbashを明示的に選ぶようにした**。Windowsには
   bashが複数あり、PowerShellから `bash` を呼ぶとPATH先頭の
   `C:\Windows\System32\bash.exe`＝**WSL**が選ばれる。WSLからはWindows側の
   127.0.0.1で待つスタブサーバーに届かず、Windows絶対パスも解決できないため
   bashが127を返し、**検査が「14件NG」に見えていた**（＝検査が壊れているように
   見えるが、実際は呼び出し元のシェルの違い）。Git同梱のbashがあればそれを優先する。
   スクリプトのパスもリポジトリ相対に変えた。

**確認済み**: PowerShellから `npm run check` が exit 0（tsc / check.ts / check-threads /
check-verify-production / check-gsc / check-probe-series の6つすべて）。
`check-verify-production.js` は17項目OK・15シナリオでNG検出のまま＝検査は緩んでいない。

**この節の教訓**: 「ローカルでも実行できる」と手順書に書いてあることは、**書いた環境でしか
確かめられていない**。書いた側が使うシェル・OSと、次に読む人が使うそれは違う。

### 追記3: 上の仕組みが実際に1件捕まえた（2026-08-16）

追記2で入れた「CIをubuntuとwindowsの両方で回す」が、**初めて自分の役目を果たした**。

`main` 側で追加された `scripts/track-season.js`（クール別の初出日の記録）が、
追記1とまったく同じ形――`process.exit(1)` が2箇所――で入っていた。`main` のCIは
ubuntuだけなので緑のまま通っており、このブランチへ取り込んだ瞬間に
`check-track-season.js` が `3221226505 !== 1`（0xC0000409）で落ちた。
**「失敗したときに1を返す」ことを確かめる検査が、Windowsでだけ通らない**という、
追記1で直したのと同じ壊れ方である。

対処も同じで、2箇所とも `process.exitCode` に置き換えた（`node scripts/check-track-season.js`
が exit 0、`npm run check` も全件緑になることを確認済み）。

**確認できたこと**: この形のバグは**書いた人の環境では絶対に見えない**
（cloudセッションはLinuxで走る）。手順や注意書きでは防げず、CIに開発機と同じOSを
含める以外に検知する方法が無い。追記2の判断はこの1件で裏が取れた。

**新しい検査を足すときの注意**: `main` 側は `npm run check` を持たない時期があり、
CIにだけ検査ステップが足されていた。マージ時は**CIの `run:` と `package.json` の
`check` の両方に同じものが並んでいるか**を確かめること（`node scripts/check.ts` の
「検査を回す環境」節が機械的に検査するので、片方だけだと落ちる）。

#### 実装当日に見つかった5件の不備（同日中に修正）

最初の実装（`lib/serviceDataset.ts`の初版）には次の5件の不備があり、公開前の同日中のレビューで
見つかって直った。**特に1・2は「無料公開して被リンクを得る」という施策の前提そのものを壊す種類の
欠陥**だったため記録しておく（失敗の記録は消さない。同じ抜けを次に繰り返さないため）:

1. **公開データセットにTV除外パターンを入れ忘れていた。** `lib/services.ts`の`SERVICES`（配信サービス
   の判定パターン）だけを配布し、放送局を除外する正規表現（`TV_PATTERN`）を含めていなかった。この
   状態のまま「二次利用側が手順どおり実装すれば本サイトの判定を再現できる」とドキュメントに書いて
   いたが、実際に配布された手順で組むとTOKYO MX・AT-X・BS11・テレビ東京がすべて「その他配信」＝
   配信サービスとして残ってしまう。**本サイトの判定を再現できない状態のまま「再現できる」と書いて
   いた**ことになる。`TV_PATTERN`を`lib/services.ts`から`export`し、`matching.broadcastPattern`として
   「①サービス→②放送局（除外）→③その他配信」の判定順序ごと配布する形に直した
   （`lib/serviceDataset.ts`の`MATCHING_NOTE`/`BROADCAST_PATTERN_NOTE`）。
2. **出典表記が誤ってAnnictをクレジットしていた。** 既存の`attributionText()`（`lib/attribution.ts`。
   作品データ表示用）をそのまま流用し、「データ元: Annict」と表記していた。この名寄せ表はAnnictの
   データを1件も含まない（本サイトが自前で書いた正規化ロジックの配布物）ため、事実として誤った出所の
   表明だった。しかも**この公開の狙いは被リンクを得ることそのもの**なので、誤クレジットは獲得したい
   被リンクをAnnictへ誤誘導する向きにも働く。名寄せ表専用の`datasetAttributionText/Html/Markdown`
   （`lib/attribution.ts`。Annictを名乗らない）を新設して差し替えた
3. 応答に`checkedAt`/`generatedAt`という日付フィールドを持たせていたが、このAPIはAnnictから何も
   取得しておらず日付に意味が無かった（かつ`s-maxage=86400`でCDNに載るため最大8日ずれた値が配られる）。
   中身が`SERVICES`と`TV_PATTERN`だけで決まる決定的な応答にし、日付フィールド自体を削除した
4. `?format=`（値を付けない）や`?format=CSV`（大文字）が400エラーになっていた
   （`searchParams.get("format") ?? "json"`は空文字を弾かない）。`parseFormat()`を新設し、未指定・

### やったこと2: 配信情報を構造化データ（JSON-LD）で機械可読にする

作品ページのJSON-LDは声優・監督・製作会社・原作者を持っていたが、サイトの中心的な事実である

#### `WatchAction`を一度実装して撤回した（同日。再提案しない）

最初の実装は`potentialAction`に schema.org の`WatchAction`を並べていた。実装後のレビューで、
**可視テキスト側で守っているルールを機械可読側で3つ同時に破る**と分かったので取り下げた。
3つとも原因は`WatchAction`という語彙を選んだこと自体にある:

1. **放送開始前の作品にも出ていた。** 門番が`airingStatus === "finished"`だけで、まだ1話も配信されて
   いない作品（`airing`扱い）は素通りしていた。「放送開始1週間前ルール」（放送開始前に視聴を示唆しない）
   を機械可読の層で破っていたことになる
2. **`target`がサービスのトップページだった。** `WatchAction`の意味は「この作品を視聴する動作の実行先」
   なので、ラベル（この作品を見る）と行き先（サービスのトップ）がズレる。⑦-7の「リンクの見た目＝遷移先」
   の機械可読版で、本プロジェクトではインシデント級に扱う型
3. **見放題であることを示す`Offer`が無い。** 機械は「無条件で見られる」と読む。レンタルを構造化データから
   外した理由（価格を表せないので並べると誤読される）が、そのまま自分に返ってくる

代わりに`additionalProperty`（`PropertyValue`）で**事実だけ**を述べる。「この作品にはこれらのサービスの
配信情報がある」は放送前・放送中・放送終了のどれでも真で、行為も行き先も主張しない。だから
**放送状態で分岐する必要が無く**、分岐が無いぶん「放送終了や放送開始前に現在形を出す」壊れ方が構造的に
起こらない。`officialUrl`も引かないので URL を1つも持たず、広告リンクが混入する経路も存在しない。

可視テキスト側で既に守っている制約を、機械可読側でも同じ強さで適用している:

- **`PropertyValue`はサービスの表示名だけを値に持つ。** `buildStreamingProperties`は`{ name }`しか
  受け取らず URL を組み立てない＝呼び出し側にアフィリエイトリンクを渡す口が構造上無い
- **property名に現在形の語（配信中・視聴できます等）を使わない。** 放送終了クールの作品にも同じものが
  出るため。名前は可視テキストの`availabilityLabel("finished")`と同じ「配信情報」の語に揃えた
  （`STREAMING_PROPERTY_NAME = "配信情報のあるサービス"`）
- **0件なら`additionalProperty`ごと出さない**（配信情報が無いことを空の器で主張しない）
- 取得元・取得日を「確認日」と書かない（⑰と同じ語の禁止。Annictから取得した日であって配信の可否を
  誰かが確認した日ではない）

検査は`node scripts/check.ts`の「配信情報の構造化データ」節。`app/anime/[id]/page.tsx`の生成箇所を直接
読み、`additionalProperty`が`buildStreamingProperties`の結果だけから来ること（直書きに戻っていない
こと）を見る。いちばん重要なのは**逆戻りの禁止**で、`WatchAction`/`potentialAction`/`EntryPoint`/

## ㉙ 作品ページだけ「配信情報なし」になっていた件（2026-08-16修正・重大度高）

### 何が起きていたか

利用者からの指摘: シーズン一覧には配信サービスが出るのに、同じ作品の**作品ページだけ**
「配信情報なし」になる作品がある。実例は `/anime/17359`（スティール・ボール・ラン
ジョジョの奇妙な冒険 2nd & 3rd STAGE・2026秋）で、一覧では Netflix のバッジが出るのに
作品ページには何も出ていなかった。

原因は⑦-4や⑳と同じ「**画面にエラーが出ない壊れ方**」で、Annict の GraphQL の
null 伝播だった。

- Annict の `Program.episode` は **non-null** として定義されている。
- ところが「話数がまだ紐付いていない program」が実在する。
- そこに `episode` を要求すると Annict は `Cannot return null for non-nullable field
  Program.episode` を返し、GraphQL の仕様どおり **program ノードが丸ごと null** になる。
- ノードごと消えるので、`channel`（＝配信サービス名）も一緒に消える。

これ自体は 2026-07-12 に一度踏んでおり（経緯は`lib/annict.ts` の
`PROGRAMS_QUERY_LIST` のコメントに残っている）、そのときは「**300件を超えた分の追い取得**」だけを直していた。
しかし**1ページ目を取る `WORK_QUERY`（作品個別取得）自体が `episode` を要求したまま**
だったため、programs が数十件しかない作品でも同じことが起きていた。一覧
（`SEASON_QUERY`）は `episode` を要求しないので、**一覧と作品ページで答えが食い違う**。

### 実測（2026-08-16・Annict本番）

同じ作品を「episode あり」「episode なし」の2通りで引いて比べた。

| 作品 | programs | episode要求時のnull | 消えたもの |
|---|---|---|---|
| 17359 スティール・ボール・ラン | 11件 | **11件（全滅）** | Netflix |
| 17433 カードファイト!! ヴァンガード Divinez | 21件 | **21件（全滅）** | 放送7局 |
| 16468 ブチ切れ令嬢 | 252件 | 147件 | UTYテレビ山梨 |

クール単位では **2026-autumn 99作品中2件・2026-summer 148作品中2件**（2026-spring と
2025-autumn は0件）。件数は少ないが、当たると**その作品の配信情報が全部消える**。
しかも話数の紐付けは新しい作品ほど遅れるので、**これから始まるクールの作品ほど当たりやすい**
＝サイトの価値がいちばん高い場面で壊れる。

なお `rebroadcast` は nullable なので、要求してもノードは消えない（同日実測）。
消える原因は `episode` だけである。

### 影響範囲

`fetchWorkById` の結果は作品ページ以外にも流れるため、同じ嘘が4か所に載っていた。

| 面 | 出ていた内容 |
|---|---|
| 作品ページ `/anime/[id]` | 「配信サービスは現時点でAnnictに登録がなく確認できません」 |
| 公開API `/api/work/[id]` | `services: []` |
| 埋め込みウィジェット（他人のサイト） | 配信先が空のカード |
| JSON-LD の `additionalProperty` | 配信サービスの記載なし |

⑰で決めた「確認していないことを確認済みのように書かない」の**裏側**にあたる誤りで、
実際には配信されているのに「登録がない」と機械可読の層まで含めて断言していた。

### どう直したか

**配信サービスを数えるための取得では `episode` を要求しない。** `lib/annict.ts` の
programs フィールドを用途別の3つの定数に分け、クエリはそこから組み立てる。

| 定数 | 中身 | 使うクエリ |
|---|---|---|
| `PROGRAM_FIELDS_LIST` | `channel` / `startedAt` | `SEASON_QUERY`・`PROGRAMS_QUERY_LIST`（一覧） |
| `PROGRAM_FIELDS_DETAIL` | ＋`rebroadcast` | `WORK_QUERY`・`PROGRAMS_QUERY_DETAIL`（作品個別） |
| `PROGRAM_FIELDS_EPISODE` | ＋`episode` | `PROGRAMS_QUERY_EPISODE`（**通知だけ**） |

話数（`episode`）が要るのは**配信開始通知メールの「第5話」表示だけ**なので、そこだけ
`fetchWorkById(id, token, { withEpisode: true })` で2本目のクエリを投げ、
`mergeEpisodeInfo` が **チャンネル名＋`startedAt`** を鍵に話数だけを重ねる。重ねる側は
**base のノードを絶対に減らさない**（episode 側で null になったノードは「話数が未紐付け」と
いう意味しか持たないため、それを理由に消すと `episode` を直接要求したのと同じ事故になる）。

`rebroadcast` は作品個別のクエリに残した。通知バッチは「今日・**再放送でない**番組」を
探すので、`episode` を外した副作用でこれまで落とすと、再放送の日に誤って通知が飛ぶ。

追い取得ヘルパー（旧 `fetchRemainingPrograms`）は `fetchProgramsPaged` に変え、
**クエリを必須引数にした**（既定値が `episode` 付きだったことが今回の遠因）。

### 確認したこと（2026-08-16・本番ビルド＋実データ）

- `fetchWorkById` → `toAnimeDetail` の経路で 17359 が `[netflix]` を返す。
- **一覧経路と作品ページ経路の突き合わせ: 2026-autumn 99作品・2026-summer 148作品で
  差分0件**（修正前は各2件）。
- `npm run build` した本番ビルドを `localhost:3100` で起動して実HTMLを取得（⑲と同じ方法）:
  - 作品ページ本文 … 「〜は Netflix（ネットフリックス） で視聴できます（2026-08-16時点）」
  - `/api/work/17359` … `services: [{key: "netflix", ...}]`
  - `/embed/anime/17359` … Netflix バッジあり
  - JSON-LD … `additionalProperty: [{"name":"配信情報のあるサービス","value":"Netflix"}]`
- 通知経路（`withEpisode: true`）… 16468 で programs 252件が1件も欠けないまま、話数が
  取れた105件にだけ `episode` が乗る。`rebroadcast` は252件すべてに入る。

### 再発防止

`node scripts/check.ts` の「シーズン一覧の追い取得クエリ」節を拡張した（2026-07-12の
既存2件はそのまま残してある）。ネットワークには出ない。

- `SEASON_QUERY` / `WORK_QUERY` / `PROGRAMS_QUERY_DETAIL` / `PROGRAMS_QUERY_LIST` が
  `episode` を**含まない**こと、`PROGRAMS_QUERY_EPISODE` だけが含むこと
- `WORK_QUERY` / `PROGRAMS_QUERY_DETAIL` が `rebroadcast` を**含む**こと（再放送の誤通知よけ）
- `lib/annict.ts` の中で `episode { number numberText }` と書いてよいのは
  `PROGRAM_FIELDS_EPISODE` の1箇所だけであること（別の場所にクエリを手書きされると
  上の検査をすり抜けるため）
- `withEpisode: true` を使ってよいのは `app/api/notify/run/route.ts` **だけ**であること
  （作品ページや公開APIが話数欲しさに立てると「配信情報なし」が復活する）
- `mergeEpisodeInfo` が base のノードを減らさないこと・話数だけを重ねること・
  episode 側が全滅（17359 の形）でもチャンネルが残ること

**この検査を消さないこと。** 逆に入れてみて落ちることも確認済み（`PROGRAM_FIELDS_DETAIL` に
`episode` を戻すと3件NGで終了コード1）。

### 教訓

2026-07-12 の修正は**症状が出た経路（追い取得）だけ**を直しており、同じフィールドを要求する
もう1本のクエリ（`WORK_QUERY`）を見ていなかった。原因が「特定のフィールドを要求すること」
そのものにあるときは、**そのフィールドを要求している箇所を全部数える**こと。今回の検査を
「クエリ単位」ではなく「`lib/annict.ts` 全体で1箇所だけ」という形にしたのはそのため。

## ㉚ 部分失敗した投稿先が再試行されず、その日ぶんが消えていた（2026-08-17修正）

### 症状

2026-08-17の夕方枠（18〜21時 JST）で、Bluesky が `TypeError: fetch failed`
（一時的な通信エラー。約5分でタイムアウト）で落ち、Threads だけ成功した。
Issue「SNS自動投稿が失敗しています」（#75）は立ったが、その本文は

> 全滅した回は投稿済みの印を残さないので、同じ時間帯の次の起動（1時間後）が自動で再試行します。

と案内していた。ところが**次の起動（19:08 JST）では Bluesky が丸ごとスキップされ**、
その後の3回の起動でも投げられないまま夕方枠が終わった。
**Blueskyの夕方枠は、その日ぶんが永久に落ちた。**

### 原因

「投稿済みの印」が **Bluesky と Threads で1つを共有**していた。

```yaml
if: steps.bluesky.outcome == 'success' || steps.threads.outcome == 'success'
```

つまり**どちらか片方でも成功すれば枠ごと投稿済み**になる。Threads が成功したので
印が残り、次の起動は「この枠はもう投げた」と判断して枠ごとスキップした。

Issue本文の案内が当てはまるのは**全滅した回だけ**で、今回のような部分失敗には効かない。
案内を信じて待つと直らない、という点で通知そのものが誤誘導になっていた。

なお当時のコメントには「Bluesky/Threads（時間帯の枠）とMastodon（1日1回のまとめ）は
別々の印にする。片方だけ失敗した日に、もう片方の再試行まで止めてしまわないため」と
**正しい意図が書かれていた**。分け方が Mastodon 対 それ以外 で止まっており、
Bluesky と Threads の間が分かれていなかった。

### なぜ単純な直し方では駄目なのか

素直に思いつくのは「枠の印を**全部成功したとき**だけ残す」だが、これは
**2026-08-05の二重投稿事故（⑦-9）と同じ形**になる。再試行の回で、既に成功していた
Threads にもう一度投げてしまうためである。

「印を残さない」と「二重投稿しない」を同時に満たすには、**印を2段にする**しかない。

### どう直したか

| 印 | キー | 残す条件 | 役割 |
|---|---|---|---|
| 投稿先ごと | `posted-bluesky-<枠>-<日付>` / `posted-threads-<枠>-<日付>` | その投稿先が成功したとき | 再試行時に**成功済みの側を止める** |
| 枠ぜんぶ | `posted-<枠>-<日付>` | **失敗が1つも無い**とき | 枠を終わらせる |

各投稿ステップは自分の印で門番する。これで、

- 部分失敗 → 枠の印は残らない → 次の起動が同じ枠を拾う →
  成功済みの側は自分の印で止まり、**失敗した側だけ再試行される**
- 全成功 → 両方の印＋枠の印が残る → 枠は終わり
- 全滅 → 何も残らない → 丸ごと再試行

`mark_only`（手で投稿した日に印だけ残す）も、投稿先ごとの印を残すようにした。
残さないと、その日の残りの起動で再試行が走ってしまう。

Issue本文の案内も「失敗した投稿先は次の起動が再試行します（成功済みの投稿先は
投稿先ごとの印で止まるので二重投稿にはなりません）」に直した。

### この形の壊れ方に共通すること

CLAUDE.mdの基本ルールは「複数件を投げるループは1件ずつ try/catch で独立させ、
1件目の失敗で残りを巻き添えにしない」と言っている。**投稿ステップ自体は独立していた**
（⑦-8で直してある）。独立していなかったのは**その結果を記録する側**だった。
「処理を独立させる」ときは、成否の記録も同じ粒度で分けること。

### 追記1: 生成スクリプトが`process.exit()`を使っていて、Windowsで終了コードが化けていた

`check-fetch-upcoming.js`を12回連続で回したところ**1回だけ落ちた**。原因は
`fetch-upcoming.js`が`process.exit(1)`を使っていたことで、Windowsでは書き込み途中の
stdoutを巻き込んでプロセスが異常終了し、終了コードが`1`ではなく**3221226505
（0xC0000409 = STATUS_STACK_BUFFER_OVERRUN）**になる。㉔で`probe-series.ts`が踏んだのと
**同じ罠**で、`track-season.js`には既に「`process.exit()`ではなく`exitCode`」という
注記があったのに、それを手本にした新しいスクリプトで再発した。

これは**CI（ubuntu）では原理的に起きない**ため、Windowsを`ci.yml`のmatrixに残していない
限り永久に緑のままになる。`process.exitCode = 1`＋`return`に直した（テスト側も同じ）。
**新しいCLIスクリプトを書くときは`process.exit()`を使わないこと。**

足すだけで、既存ページが1つも下がらなくても数字は悪化する**（構成比の移動）。

**表示の12.2%しか占めない面が悪化の70%を作っていた。** 除くと週次平均は

## ㉝ ㉜の診断が部分的に誤っていた件と、その訂正（2026-08-31）

28日集計は表示6,300×22.25位＝重み付き合計140,196。10未満にするには63,000未満が必要。

### 教訓（㉜の教訓を差し替え）

㉜は「効いている面だから広げる、は条件を確かめないと逆効果」と書いた。それは正しい。
だが**その反省自体を、部分データで急いで実装したために二度目の誤りを重ねた**。
順序として正しいのは:
①完全な期間のデータで測る（`partial` を見る）→ ②外す候補が本当にクリックを
取っていないか**ページ単位で**確かめる → ③粒度（年か、クールか）を検索語から決める →
④実装する。②を飛ばすと、直したつもりで収入を捨てる。
