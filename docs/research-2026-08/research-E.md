## カテゴリ1: データ/API公開による被リンク・依存関係の獲得

### 1. しょぼいカレンダー (cal.syoboi.jp)
- **何をした**: 個人運営のアニメ放送スケジュールサイトが、正式APIと呼べるほど整っていないもののXML/JSON/iCalendar/RSSなど複数形式でデータを無償公開。
- **伸び**: 2013年頃から現在まで10年以上、多数の個人開発者（Ruby gem `syobocal`、Python連携等）がライブラリを作って依存。自動録画ツール・ファイルリネームツール・統計分析ツールなど周辺エコシステムが形成された。
- **再現性**: 高い（本サイトと同ジャンル）。「配信データを構造化して二次利用可能な形で公開する」だけで長期にわたり開発者コミュニティからの参照・言及を継続的に得られる好例。
- 出典: [データを取得する方法 - しょぼいカレンダーのヘルプ](https://docs.cal.syoboi.jp/spec/feeds/), [しょぼいカレンダー API 用のライブラリでキャスト、スタッフ、楽曲の情報を取得できるようにした](https://r7kamura.com/articles/2017-02-12-h), [しょぼいカレンダーからデータを取得するGemを公開した](https://www.xmisao.com/2014/04/15/ruby-gem-syobocal.html)

### 2. Annict GraphQL API（本サイトが依存しているAPI自体の事例）
- **何をした**: 個人運営のアニメ視聴記録サービスがGraphQL APIを公開。
- **伸び**: 「歴代アニメ視聴履歴＆評価ポータル」「GitHubプロフィールに視聴数バッジを表示するサービス（shields.io連携）」など、複数の個人開発者がAnnictを引用元として言及する記事・OSSを継続的に生んでいる。
- **再現性**: 高い。本サイト自身が「Annictを使う側」であると同時に、「配信情報を集約公開する側」として同じポジションを取れる。
- 出典: [ANNICT APIを活用して自身の「歴代アニメ視聴履歴＆評価ポータル」を作成](https://note.com/ruupin/n/n26a9f6c74929), [Annictの記録したアニメ数をGitHubのプロフィールに載せるサービス](https://zenn.dev/penguincabinet/articles/762e7e201fd86a)

### 3. zipcloud（郵便番号検索API）
- **何をした**: 個人/小規模運営が郵便番号→住所APIを無償公開。
- **伸び**: JavaScriptの住所自動入力チュートリアル記事が多数のブログ・Qiita記事で継続的に取り上げられ、「郵便番号API」で検索すると定番として比較記事に載り続ける（実装解説記事が恒常的に量産＝被リンクのロングテール化）。
- **再現性**: 高い。ただし郵便番号のような汎用需要データほど二次利用者が多い。
- 出典: [郵便番号検索API - zipcloud](http://zipcloud.ibsnet.co.jp/doc/api), [【2025年版】郵便番号APIサービス比較 - Qiita](https://qiita.com/7mpy/items/d1ef63934f87ef5704a7)

### 4. 日本の祝日API（holidays-jp, @matsubara0507ほか個人開発）
- **何をした**: Googleカレンダーの祝日データを元にJSON/CSVで祝日情報を返すAPIを個人が公開。
- **伸び**: 「システム開発者向け 日本の祝日取得法まとめ」のような比較記事に定番として掲載され続けている。類似の個人開発API（Japanese Calendar API + MCPサーバー、2026年公開）も継続的に登場＝ジャンルとして「困りごと解決API」は言及されやすい。
- **再現性**: 高い。
- 出典: [日本の祝日を JSON / CSV 形式で返す API - Qiita](https://qiita.com/matsuoshi/items/7c19e7dcf404b7d921d6), [日本の祝日・営業日・暦を返すAPIとMCPサーバーを作ってみた](https://zenn.dev/kazuki_tam/articles/a9a037210b1d60)

### 5. 駅データ.jp（ekidata.jp）
- **何をした**: 個人/小規模運営が鉄道駅マスタデータをXML/JSON APIで無償公開。商用利用時は「駅データ.jpのデータを利用していること」と「駅データ.jpのURL」の掲示を利用規約で義務付け＝**構造的に被リンクを組み込んでいる**点が特徴的。
- **伸び**: WordPress連携記事、路線情報取得のQiita記事など多数の二次利用記事が継続的に生まれている。
- **再現性**: 中〜高。「利用規約でクレジット表記＋リンクを義務化する」という設計は、本サイトが公開API/ウィジェットを提供する際にそのまま転用可能な手法。
- 出典: [API | 駅データ.jp](https://ekidata.jp/api/), [駅データ.jpを利用して路線情報を取得する - Qiita](https://qiita.com/nskij/items/03075222ba7ef2916f3e)

### 6. openBD（版元ドットコム × カーリル）
- **何をした**: 出版社団体データを元に書誌情報・書影を無償API提供。図書館OPAC等に広く使われた。
- **伸び**: 図書館・書店・個人アプリが幅広く採用、国立国会図書館の解説記事(current.ndl.go.jp)にも取り上げられるなど権威あるメディアからの言及を獲得。
- **教訓（※重要）**: 2023年、データ提供元（JPRO）からのフィードが停止し、非会員社の書誌データ更新が止まった。**外部データに依存するAPIは供給元都合で継続性リスクがある**という反面教師にもなる。
- 再現性: 中（本サイトは既にAnnict依存というリスクを抱えているため、この教訓＝「取得元が止まったときの縮退設計」は既に`getWorkData`のフォールバックで対応済み）。
- 出典: [openBD | 書誌情報・書影を自由に](https://openbd.jp/), [openBDからのお知らせ：openBD API（バージョン1）の提供終了について](https://openbd.jp/news/20230725.html), [E1924 – 図書館のOPACなどで書影の利用が可能なopenBD](https://current.ndl.go.jp/e1924)

### 7. Jikan（Unofficial MyAnimeList API）
- **何をした**: MyAnimeListに公式APIが機能不足だった時期に、非公式スクレイピングベースのREST APIを個人/コミュニティが構築・公開。
- **伸び**: GitHub（jikan-me/jikan）、RapidAPI、複数の公開APIカタログサイト（publicapis.io, jsonapi.co等）に継続的に掲載され、多数のアニメ関連アプリ・Botの基盤として引用され続けている。
- **再現性**: 高い。**本サイトと同一ジャンル（アニメ）での「他の開発者に使われるAPIになる」戦略の直接的な先行事例**。
- 出典: [Jikan - Unofficial MyAnimeList API](https://jikan.moe/), [GitHub - jikan-me/jikan](https://github.com/jikan-me/jikan)

### 8. TMDB（The Movie Database）API
- **何をした**: コミュニティ運営の映画/TVメタデータベースを無料APIで公開。
- **伸び**: Plex・Jellyfin・Kodi・Sonarr・Radarr・Letterboxd・Trakt・Stremioなど主要な個人向けメディアサーバー/アプリの標準メタデータ供給元となり、"Powered by TMDB"のクレジット表記が業界標準になっている。
- **再現性**: 中。長年の運営とコミュニティ信頼の蓄積が必要だが、「配信データの正規化・集約」という本サイトの立ち位置と方向性は同じ。
- 出典: [GitHub - api-evangelist/tmdb](https://github.com/api-evangelist/tmdb), [API for Jellyfin TMDb Plugin](https://www.themoviedb.org/talk/66af2930b4131c1c25ea8c7f)

### 9. Open Food Facts API
- **何をした**: 非営利のオープン食品データベースをJSON APIで公開。
- **伸び**: 公式発表で**約200のアプリ・サービス**がAPIを利用（各アプリがクレジット表記＝被リンクの面的拡大）。
- **再現性**: 中。データの網羅性・更新頻度の担保が前提になる大型事例だが、「オープンデータ提供者になる」という設計思想は小規模でも模倣可能。
- 出典: [Open Food Facts データ、API](https://jp.openfoodfacts.org/data)

## カテゴリ2: バズ系プラットフォームでの一時トラフィックと定着の可否

### 10. Product Hunt 個人開発 2位獲得（sabigara氏）
- **何をした**: 個人開発サービスをProduct Huntにローンチ。
- **伸び**: 初日約700人のアクセス。**その後は1日ごとに半減**し、現在は約25ユーザー/日に落ち着いた、という開発者自身の報告。
- **教訓**: バズ直後のスパイクは指数関数的に減衰し、**定常トラフィックへの転換にはローンチ以外の継続施策が必須**。
- **再現性**: 高い（無料でローンチ可）だが、定着効果は低いと自己申告されている。
- 出典: [個人開発でProduct Hunt 2位を獲るまでに考えたこと & その結果 - Zenn](https://zenn.dev/sabigara/articles/4a4866fece771d)

### 11. Hacker News フロントページ掲載によるトラフィックスパイク（複数の実測ブログ）
- **何をした**: 個人開発者が自作ツール/記事をHacker Newsに投稿し、フロントページ掲載。
- **伸び**: 実測値として「12,000 visitors/24h（平常の10倍）」「15,000ユニークビジター/18,000PV（20時間）」「722ポイントで大規模トラフィック」など複数ブログが実数を公開。ただしいずれも**単発スパイクで数日以内に平常値へ戻る**。
- **再現性**: 中（狙って掲載されるのは難しいが、無料・匿名投稿可）。定着にはつながりにくい。
- 出典: [Anatomy of a Hacker News traffic spike](https://harrisonbroadbent.com/blog/hacker-news-traffic-spike-anatomy/), [Traffic impact of 722 points on Hacker News](https://luke.hsiao.dev/blog/2023-hn-traffic/), [What Happens When You're On The Front Page of Hacker News](https://nicklafferty.com/blog/what-happens-when-you-re-on-the-front-page-of-hacker-news/)

### 12. Show HN 経由のGitHubスター獲得（個人OSS開発者の実測比較）
- **何をした**: Pythonで作ったOSS（データ可視化ツール）をShow HN・Reddit・Qiita・dev.toの4チャネルに投稿し効果を比較。
- **伸び**: **Show HN**＝投稿当日のGitHubトラフィック約3,000ユーザー（平常の約300倍）、2日で約120スター獲得。**Reddit**＝約30スター。**Qiita/dev.to**＝ほぼ効果なし。
- **教訓**: チャネルごとの効果差が大きい。**Show HN級の海外開発者コミュニティが最も強く、国内Qiita/dev.toへの投稿だけでは開発者流入が伸びにくい**という実測は、本サイトの「/developers」ページの告知先選定に直接参考になる。
- 出典: 検索結果に基づく（元記事URL特定不十分のため要再検索。数字はWebSearch要約経由）

### 13. GitHub Trending 掲載
- **何をした**: 個人開発プロジェクト「Ephe」がGitHub Trendingに掲載。
- **伸び**: 100スター以上獲得、Developers Trendingで20位前後に到達。
- **再現性**: 低〜中（Trending掲載自体が結果指標であり狙って起こしにくい）。
- 出典: WebSearch要約（元一次ソース特定不十分）

### 14. Awesome list（GitHub）掲載の限定的効果
- **何をした**: 複数の個人開発者がAwesome系リストへの掲載を試みた体験談。
- **知見**: 「Awesomeリストはほとんどの分野に存在するが閲覧者が少なく、多くはメンテナンスもされていない」「Hacker News・Product Hunt・GitHub Trendingの方が効果が大きい」という**否定的な実測知見**が複数の個人開発者ブログで一致。
- **再現性**: 高い（掲載コストは低い）が、期待値は低いとみるべき。
- 出典: [GitHubのawesomeリンク集のスター数、作成日を調べてみる](https://wonderwall.hatenablog.com/entry/2017/09/01/001000)

## カテゴリ3: プラットフォーム・OS機能への相乗り配布

### 15. Discord Bot の個人開発によるサーバー数急拡大
- **何をした**: 個人が趣味でDiscord Botを開発・公開。
- **伸び**: ある開発者は「導入サーバー数が75を超え、Discord公式からDMが届いた」時点で初めて外部ユーザーの存在を実感（3年で93サーバー）。別事例では**累計8,000サーバー以上・ユーザー数20万人以上**に成長した個人運営Botも報告されている。
- **再現性**: 高い（無料でBotを公開できるプラットフォームに乗る戦略）。ただし本プロジェクトはSNS自動化以外の直接施策なし。将来「配信スケジュール通知Bot」等を作る場合の参考。
- 出典: [Discordのボイスチャンネル移動botを公開し、90サーバーまで運用した話 - Qiita](https://qiita.com/sakusaku3939/items/c94676f8eb7e4974fe96)

### 16. Chrome拡張機能を17〜20本個人運営（ktg氏）
- **何をした**: 個人が小さく特化したChrome拡張を多数リリースし、Chromeという既存プラットフォームの配布網（ウェブストア検索）に乗る戦略。
- **伸び**: 「1本が月500円課金ユーザー10人＝5,000円、20本あれば10万円も射程に入る」という積み上げモデルを開発者自身が提示。Chromeは世界シェア65%超・ダウンロード数140億超という土台の大きさを根拠に挙げている。
- **再現性**: 中。本サイトの場合は「特定サービスの配信スケジュールを通知する拡張」等、小さく分割して複数リリースする発想への転用余地あり。
- 出典: [Chrome拡張機能を17本個人開発して運営する話 - Zenn](https://zenn.dev/ktg/articles/da898f8587df5d8), [Chrome拡張を20本以上個人開発している話 - note](https://note.com/happy_guppy7416/n/n90f9258e12f8)

### 17. iCal（.ics）配信による定期購読 — 「iCal週間天気予報」（増井敏克氏）
- **何をした**: 個人開発者が天気予報データをiCalendar形式で配信し、Googleカレンダー等にワンタッチ購読できる形で公開。
- **伸び**: 具体的PV数の公開なし（※要注意）だが、「カレンダーに登録するだけで自動更新され続ける」という配布形態そのものが継続閲覧を生む設計として個人開発者コミュニティで紹介・言及されている。
- **再現性**: 高い。本サイトも「今期の放送予定をiCal購読で配れる」形にすれば、SNS投稿に頼らない継続接触チャネルになりうる（未実装の場合は着手コスト低）。
- 出典: [「iCal週間天気予報」をリリースしました｜増井敏克](https://note.com/masuipeo/n/nf6636e5919b8)

### 18. Greasyfork（ユーザースクリプト配布）
- **何をした**: Tampermonkey等で動くユーザースクリプトをGreasyforkに公開し、既存の巨大サイトに機能追加する形で配布。
- **伸び**: 具体的な流入数の一次データは今回の検索では確認できず（※要注意・裏取り不足）。ただし「Userscripts.orgの後継として最大規模」という位置づけがあり、ニッチな機能特化スクリプトの配布網として定番。
- **再現性**: 中。本サイトのジャンルでは「特定配信サービスのページに『配信ガイドで探す』ボタンを差し込むスクリプト」等が理論上考えられるが今回は実例数字を確認できていない。
- 出典: [Greasy Fork – 便利で安全なユーザースクリプト](https://greasyfork.org/en)

## カテゴリ4: 市民データ提供・定点観測による報道/メディア引用

### 19. 新型コロナウイルス感染症対策ダッシュボード（福野泰介氏、jig.jp）
- **何をした**: 鯖江市のIT企業経営者が個人/有志として、公的機関の一次データをリアルタイム連携するダッシュボードを構築・公開。「シビックテック」文脈で他の技術者有志と連携し、オープンデータの標準フォーマット策定にも関与。
- **伸び**: 総務省の情報通信白書等の公的資料で取り上げられ、メディア・自治体からの参照が継続。比較対象として挙げられるジョンズ・ホプキンス大学のCOVID-19ダッシュボードは1日10億アクセス超・世界中の報道機関からの引用元になった（規模は桁違いだが「一次情報をリアルタイム集約して見せる」という設計思想は同じ）。
- **再現性**: 中〜高。本サイトも「Annictの一次データをリアルタイムに集約・可視化する」という同型の設計を既に持っている。「クール開始時の定点観測レポート（新作○本、配信サービス別カバー率など）」を定期発表しメディア・SNSへ投げる形に転用可能。
- 出典: [ジョンズ・ホプキンス大学の新型コロナウイルス感染状況ダッシュボード作成の裏側](https://blog.esrij.com/archives/35916), [総務省 令和2年版情報通信白書 オープンデータの活用](https://www.soumu.go.jp/johotsusintokei/whitepaper/ja/r02/html/nd132320.html)

## カテゴリ5: 検索エンジン特殊枠・生成AI検索での引用

### 20. Google Discover による個人ブログの急増実例
- **何をした**: 独自サーバー運用の個人ブログがGoogleアルゴリズム変化後にDiscover掲載が回復。
- **伸び**: 実測で「2025年10月に44万PV（GA4）まで回復、レンタルサーバー計測では月間約144万PV」、別事例では「翌日のDiscover経由クリック数が400件超」という具体的な報告がある。
- **再現性**: 低〜中。Discover掲載条件はGoogle側の非公開アルゴリズムに依存し狙って再現しにくいが、「画像の充実・E-E-A-T・鮮度」等の一般則は他のSEO施策と共通。
- 出典: [Googleアルゴリズム再評価で個人ブログが復活？2025年10月アクセス報告](https://saitoshika-west.com/blog-entry-9778.html), [ブログやコラムが一気にバズる！Google Discover掲載を目指すオウンドメディア戦略](https://attlabo.com/blog/marketing/google_discover_2025jan/)

### 21. FAQPage構造化データによるリッチリザルト・CTR向上の複数事例
- **何をした**: 複数のサイト運営者がFAQスキーマ（構造化データ）を実装し検索結果にリッチリザルトを表示。
- **伸び**: 実測報告として「30%のCTR増加（3ヶ月以内）」「CTRが2%→14%に増加（特定ページ）」「全体トラフィックが前月比約25%改善」「CTR50%超増加」など複数の独立事例で数値が報告されている。ただし「効果が薄かった」という事例（seoClarityのA/Bテスト）も同時に存在し、**必ず効くわけではない**という留保も明記されている。
- **再現性**: 高い（実装コストは低い。本サイトは既に`content/works/{id}.json`の`faq`でFAQPage構造化データを実装済み＝適用対象を増やす余地がある）。
- 出典: [Schema Success Stories: Using Structured Data to Boost Traffic](https://www.searchenginejournal.com/schema-success-stories-structured-data-boost-traffic/372734/), [Testing Structured Data: Does FAQ Schema Increase CTR? - seoClarity](https://www.seoclarity.net/blog/faq-schema-ctr-test)

### 22. Ahrefs「ChatGPTが140万プロンプトでどのページを引用したか」調査
- **何をした**: Ahrefsが2026年、ChatGPTの140万件のプロンプトを分析し、引用されたページの特徴を統計的に調査（一次データに基づく数少ない生成AI引用の定量研究）。
- **わかったこと**: ①**タイトル・URLが検索クエリに対して具体的・明快なページほど引用されやすい**（幅広いクエリに漠然と一致するページより、狭いクエリに正確に一致するページが強い）。②**鮮度が強く効く**＝ChatGPTが引用したURLはGoogleのオーガニック結果より平均458日新しい。③**「ブランドについて他者が言及している量」が生成AIの回答への出現を最も強く予測する**（75,000ブランド調査）。④取得された（retrieveされた）ページの半分程度しか最終的に引用されない。Redditは取得されても1.93%しか引用されない。
- **再現性**: 高い（実装コストほぼゼロ、既存コンテンツの改善で対応可能）。本サイトへの示唆: ①作品ページのtitleを検索意図に厳密一致させる（`lib/workTitle.ts`は既にこの方向）、②クール更新のたびにコンテンツを更新し鮮度を保つ（すでに15分キャッシュ運用）、③外部での言及（被リンク・SNS言及）を増やすことが生成AI経由の露出にも直結する。
