# Vercel利用量の自動取得（セットアップ手順）

2026-09-15導入。Vercelの無料枠に収まっているかを**毎日機械が取ってリポジトリに置く**ための設定。
やることは**1回だけ**で、以後は自動で回る。

---

## なぜ自動化したか

- 無料枠の一次情報はVercelのダッシュボードだけ。**ログインが要るためセッション（Claude）からは読めない**
- そのため答え合わせが毎回「人が画面の数字を手で写す」まで止まっていた
- しかも目視なので**実際に2〜4倍読み違えた**記録がある（`docs/operations.md` の㉝・㊶）
- 2026-08-24には気づくのが遅れ、**本番が丸一日 HTTP 402 で停止**した
- GSC・行動ログと同じ形（GitHub Actionsが取ってJSONをコミット→セッションは読むだけ）に載せた

---

## ① Vercelのトークンを作る（所要3分）

1. https://vercel.com/account/tokens を開く
2. 「Create Token」
3. **TOKEN NAME**: `animedia-usage-readonly`（名前は何でもよいが、用途が分かるものにする）
4. **SCOPE**: 自分の個人アカウント（Hobbyならこれ1つしか出ない）
5. **EXPIRATION**: **1年**など、期限を必ず付ける（`No Expiration` は選ばない。理由は下）
6. 「Create」→ 表示された文字列をコピーする（**この画面を閉じると二度と表示されない**）

### ⚠ 先に知っておくこと（重要）

**Vercelの個人アクセストークンは「読み取り専用」にできない。**
作れるのはアカウント全体の権限を持つトークンだけで、これ1本で

- 本番へのデプロイ
- デプロイの削除
- 環境変数の読み取り・書き換え

まで**できてしまう**。いま使っている他の2つのSecretsとは性質が違う:

| Secret | できること |
|---|---|
| `GSC_SERVICE_ACCOUNT_JSON` | Search Consoleの**読み取りだけ** |
| `ADMIN_DASHBOARD_TOKEN` | 自分のサイトの集計画面の**読み取りだけ** |
| `VERCEL_TOKEN`（今回） | **アカウントに対してほぼ何でも** |

そのうえで導入する判断にしたが、次の3つは守る:

- **期限を付ける**（上の⑤）。漏れても期限で自動的に無効になる
- **GitHub Secrets にだけ置く**。チャット・PR本文・コミットに貼らない
- **どこかに貼ってしまったら、すぐ https://vercel.com/account/tokens で Delete する**（作り直せばよい）

取得スクリプト側でも、トークンが出力に混ざったら**書かずに落とす**ようにしてある
（`scripts/fetch-vercel-usage.js` の `assertNoSecrets`。回帰テストで固定済み）。
コマンドライン引数にも載せない（`ps` に出るため）。送るのはHTTPヘッダーだけ。

---

## ② GitHub Secrets に登録する（所要2分）

1. https://github.com/junatushi/animedia/settings/secrets/actions を開く
2. 「New repository secret」
3. **Name**: `VERCEL_TOKEN`（この綴りちょうど。前後に空白を入れない）
4. **Secret**: ①でコピーした文字列を貼る
5. 「Add secret」

> チーム（Team）配下のプロジェクトの場合だけ、`VERCEL_TEAM_ID` も同じ手順で登録する。
> 個人アカウント（Hobby）なら**不要**。

---

## ③ 1回だけ手で動かして確かめる（所要2分）

1. https://github.com/junatushi/animedia/actions を開く
2. 左の一覧から「**Vercel利用量の日次取得**」を選ぶ
3. 右上の「Run workflow」→ 緑の「Run workflow」
4. 1〜2分待って実行をクリックし、ログを開く

### 成功のとき

- 「利用量を取得する」に `書き出し: .../content/analytics/usage/2026-09-15.json（… 〜 …）` と出る
- 続けて `明細 N 件 / M 日分` と、上位のサービス名が並ぶ
- 「判定を出す」に指標ごとの表（1日あたり／1日の予算／30日見込み／上限／比）が出る
- `content/analytics/usage/` にJSONがコミットされる

**ここまで出たら完了。以後は毎朝5:40前後に自動で回る。**

### ④ 私（Claude）に伝えてほしいこと

- 成功したなら「取れた」の一言でよい（**数字を写す必要はない**。コミットされたJSONを直接読める）
- 失敗したなら、ログの最後の数行をそのまま貼ってほしい

## 【結論・2026-09-19 実測】Hobbyプランでは取得できない

**この自動取得は、Hobbyプランでは動かないことが確定した。** トークンを作って
GitHub Secrets に登録し、実際に走らせた結果がこれ:

```
恒久的なエラー: HTTP 404 {"error":{"code":"not_found","message":"Plan not found."}}
```

- **設定ミスではない。** トークンが無効なら 401/403 が返るが、認証は通っている
- **Hobbyは無料枠＝請求サイクルを持たない**ので、請求を前提にしたこの窓口に該当するレコードが無い
- 待っても直らず、直す手段も無い（有料プランに変える以外）
- **代わりになる公開APIも見つからなかった**（Vercelの公開RESTに、Hobbyの利用量を返す窓口は無い）

### だからどうなっているか

| いま | 誰が担うか |
|---|---|
| `vercel-usage.yml` | 毎日走るが、404「Plan not found」を**失敗ではなく省略**として扱い、理由を出して終わる |
| `scripts/freshness.js` | `usage` 系列は `blockedReason` 付きで残す（`ℹ` 表示。**赤くならないが、消えもしない**） |
| **利用量の確認** | `usage-check.yml` が判定日に出すIssue＝**ダッシュボードを目視**する従来の手順 |
| Deployment Storage | `scripts/check-build-size.js` がCIで自動判定（ここだけは自動化が効いている） |

**失敗にしない理由**: 直し方が無いものを毎朝Issueに積むと、数日で読まれなくなり
本物の障害まで一緒に見逃す（`docs/operations.md` の㉔と同じ壊れ方）。
**消さない理由**: 消すと「なぜ利用量が自動で取れないのか」がどこにも残らない。

### 有料プランに変えたら

**何もしなくてよい。** 404 が出なくなった時点で取得が動き出し、
`content/analytics/usage/` にファイルが入る。ファイルが1件でも入れば
`freshness.js` は `blockedReason` を無視して通常の欠測検知に戻る
（＝見張りが自動で復活する。回帰テスト⑧''がこれを固定している）。
そのとき `scripts/freshness.js` の `usage` 系列から `blockedReason` の行を消すと表示が整う。

### 手元で確かめたいとき

```
npx vercel@59 login
npx vercel@59 usage --breakdown daily --json
```

`vercel usage` はこの取得の元になったCLIで、中身は同じAPIを叩いている。
Hobbyなら同じように失敗するはず。出力の形は揃えてあるので、
有料プランで数字が出るならコミットされるJSONと突き合わせられる。

## そのほかの失敗

| ログに出るもの | 意味 | 対処 |
|---|---|---|
| `VERCEL_TOKEN が未設定` | Secretsの名前が違う | ②の綴りを確認（`VERCEL_TOKEN`） |
| `HTTP 401` | トークンが不正・期限切れ | ①からやり直して②を上書き |
| `HTTP 403` | このアカウントでは請求明細を読めない | 権限の無いスコープのトークン。①からやり直す |
| `HTTP 404`（`Plan not found` 以外） | teamId の指定違いなど | `VERCEL_TEAM_ID` を消す（個人アカウントなら不要） |
| `⚠ 明細が0件でした` | **利用ゼロではなく、取れていない** | 窓口はあるのに中身が無い状態。上の404とは別物 |

## 仕組み（触るときに読む）

| ファイル | 役割 |
|---|---|
| `.github/workflows/vercel-usage.yml` | 毎日1回動かす。トークン未登録なら静かにスキップ |
| `scripts/fetch-vercel-usage.js` | 取得して `content/analytics/usage/<日付>.json` に書く |
| `scripts/lib/vercel-usage.js` | 日付（LA時間）・畳み込み・**無料枠の予算表**・判定 |
| `scripts/usage-report.js` | コミット済みJSONを読んで判定を出す（**ネットワークに出ない**） |
| `scripts/check-vercel-usage.js` | 上の回帰テスト。`npm run check` とCIで回る |
| `scripts/freshness.js` | **収集が止まったら教える**（`usage` 系列として登録済み） |

### 判定の考え方

- **総量ではなく「1日あたり」で見る**。ダッシュボードのローリング30日合計には対策前の分が
  混ざるので、対策の効果が窓から抜けるまで判断できない（実際に一度誤読している＝㉝）
- 上限（30日）÷30 を1日の予算とし、実測の1日あたり×30 を見込みとして比べる
- **当日は平均に入れない**（途中までしか集計されていない＝必ず低く見える）
- **単位が予期と違えば判定しない**（保留と明記する）。請求APIの数量がダッシュボードと
  同じ単位かは実データを見るまで確定しないので、桁ごと違う数字で合否を出さない
- **予算表に無いサービス名は必ず出す**。Vercelが名前を変えたときに指標が黙って消えないように
- Deployment Storage だけは**残高**なので日割りしない（古いデプロイが消えるまで下がらない）

### 予算表を変えるとき

`scripts/lib/vercel-usage.js` の `BUDGET`。上限を書き換えるときは、
**どこから来た数字かをコメントに残す**こと（`docs/operations.md` の「数字をドキュメントに
転記しない」と同じ理由で、根拠のない数字は数セッションで意味が分からなくなる）。
